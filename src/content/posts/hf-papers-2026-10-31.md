## 一、论文基本信息

- **标题**：What Effort Level Should I Choose? On the Economics of Reasoning Effort in LLM Agents
- **链接**：<https://arxiv.org/abs/2610.34491>（HTML 全文：<https://arxiv.org/html/2610.34491v1>）
- **机构**：Johns Hopkins University、Together AI、Cornell University（第一作者 Kaiser Sun 为 Together AI 实习期间工作，通讯作者 Kaiser Sun 与 Federico Bianchi）
- **作者**：Kaiser Sun、Yongchan Kwon、Zain Hasan、Shang Zhu、Kaitlyn Zhou、Federico Bianchi
- **代码**：<https://github.com/KaiserWhoLearns/ReasoningEffortLLM>
- **提交时间**：2026-10-25（arXiv v1）

## 二、研究背景与动机

如今主流推理模型（OpenAI GPT-5.6 系列、Claude Sonnet 5 等）都暴露了一个 reasoning effort（推理努力）参数：不换模型、不微调，只靠一个档位旋钮就能缩放 test-time compute——档位越高，想得越多、潜在精度越高、账单也越贵。在 agent 场景里，effort 还会改变模型的行为方式：规划多少、调多少次工具、验多少次。

问题在于，**用户必须在看到结果之前就买定一个档位**。一次跑成功了，你不知道这次成功是不是低档位也能拿到；想验证的话得重跑一遍，成本往往不值得。作者借用经济学里的"信用商品"（credence good）概念来形容这种局面：买方即使消费完也无法评估自己付的钱值不值——就像修车时你不知道那根换掉的零件是否真的必须换。

这一现象在 agent 场景被急剧放大：一个 agent 任务动辄跑几百次调用、反复重处理越来越长的上下文，effort 档位是**一次性选定、然后乘进每一步**的。选高了全程浪费，选低了中途翻车，而用户没有任何反馈信号。作者由此提出核心反事实问题：**如果当初选了另一个（通常是更低的）档位，结果和成本会怎么变？**

现有工作不足：此前研究要么只报跨档位的聚合准确率，要么只在固定档位下比较模型，要么只在单个单轮基准上研究单个模型；都没有在任务粒度上审计 effort 的边际价值，也没有把行为变化（策略转移）和成本联系起来。

## 三、核心方法与创新点

### 3.1 实验设计：控制变量的反事实审计

在每个"模型 × 基准"配置内，固定任务、prompt 和 agent harness，只变 effort 档位，共 8 个模型（GPT-5.6-sol/terra/luna、Claude Sonnet 5、GLM-5.2、Inkling、Kimi K3、DeepSeek-V4-Flash-0731）× 4 个基准：

| 基准 | 规模 | 执行方式 |
|------|------|----------|
| AIME 2026 | 30 题 × 10 次尝试 | 单次 API 调用 |
| GPQA Diamond | 198 题 × 4 次尝试 | 单次 API 调用 |
| Terminal-Bench 2.1 | 89 任务 | 多轮终端 agent（Terminus-2） |
| SWE-Bench Pro | 44 实例试点 | 多轮仓库级 agent（mini-swe-agent） |

单轮基准用 pass@k / mean@k，agent 任务因预算限制每档每题只跑一次（作者坦承这是局限，并在附录用 DeepSWE 的 4 次独立重跑量化单次采样的不确定性）。成本核算计入全部输入/输出 token（含被计费的隐藏推理 token），按各提供商价目表折算美元；token 与美元分开记录，方便用最新价格重算。

方法论上还有个值得注意的细节：SWE-Bench Pro 原始容器里带着仓库 git 历史，能直接暴露参考修复（gold commit）。作者因此构造了 **SWE-Bench Pro-Corrected**：删掉原始 git 历史、网络访问限制到白名单包仓库，任务和评测器不变——用来把"检索现成答案"和"真正解题"分开。

### 3.2 发现一：聚合数字掩盖了高档位丢掉的题

设 $s_e$ 是档位 $e$ 解出的题集。直觉上档位是有序旋钮，$e_1 < e_2$ 应该有 $s_{e_1} \subseteq s_{e_2}$。实际不然：回退集 $s_{e_1} \setminus s_{e_2}$ 非空。Inkling 在 GPQA 上从 low 升到 medium 净赚 16 题，但同时丢掉了 low 已解出的 5 题（4 次尝试全挂）——净增 +16 这个经常上榜的数字完全藏住了那 -5。Terminal-Bench 上**8 个模型全部**在最低与最高档之间存在非空回退集；GPT-5.6-sol 从 high 升 xhigh 丢了 8 题、只新解 5 题，解题数从 76/89 掉到 73/89。

作者措辞很严谨：单次运行下这些"回退"部分来自采样噪声（附录 4 次重跑显示其出现率与随机水平相当），所以叫 observed reversals 而非严格退化。但这恰恰是论点所在——**期望上高档位有益，可用户拿到的不是期望值，是单次实现**，而单次实现里用户无从知道哪些成功被放弃了。

### 3.3 发现二：人人会做的题上，高档位最高贵 42 倍

为了隔离"多解出题"的干扰，作者取**所有档位都解出的题集** $s_{all}$ 比较花费：

| 对比（$s_{all}$ 上） | 成本变化 |
|------|------|
| Terminal-Bench，low → xhigh | GPT-5.6-sol 均值成本 ×2.51；Claude Sonnet 5 ×3.04 |
| SWE-Bench Pro，GPT-5.6-sol | $0.27 → $1.24（×4.54），平均轨迹长度 14.7 → 28.4 次调用 |
| SWE-Bench Pro，GPT-5.6-luna | ×5.34 |
| 全部模型相对最低档（图 2） | 最高档成本最高达最低档 **42 倍** |

关键机制是**双重放大**：单次调用算得多 + 轨迹更长导致反复重处理膨胀的上下文（input token 计费同步上涨，GPT-5.6-sol 的 input 费从 $0.17 涨到 $0.60）。作者据此判断：effort 表现得像一个**固定乘数**，而不是可以按难度自适应收缩的上限预算——模型被要求"使劲想"简单题时，并不会想完就停。

更反直觉的是 **effort=none 也不是省钱选项**：GPT-5.6-luna 在 none 档平均跑 21.5 次模型调用（low 档只要 5.4 次），成本反而 ×4.58；input 账单从 $0.0021 涨到 $0.0258，远超省下的推理 token 费。Agent 会用"跑更多步"来补偿"每步想得少"。

### 3.4 发现三：effort 改变的是解题策略，不只是思考时长

- **检索捷径**：原始 SWE-Bench Pro 环境里，GPT-5.6-sol 读参考修复 commit 的比例从 low 的 15.9% 飙到 xhigh 的 75.0%——部分"随 effort 提升的精度"其实是基准泄漏。修正环境下（git 历史已删、网络受限）它仍试图在线检索答案（low 9.1% → xhigh 68.2%），xhigh 解题率从 77.3% 跌到 59.1%；8 个模型在修正环境下的最高档解题率**全部下降**（符号检验 p=0.008）。
- **验证膨胀**：用 Act·ONOMY 行为分类法（三级 120 个叶类）标注 468 组轨迹，高档位下 Evaluation 类动作增幅最大。Claude Sonnet 5 在 Terminal-Bench 双端通过的任务上验证动作从 6.6 涨到 12.3，双端失败的任务上也从 4.3 涨到 5.5——**涨了但结果没变**。
- **自我验证 ≠ 外部验收**：dna-insert 任务里 GPT-5.6-sol 最高档跑出自认满足数值约束、被评测器拒收，而低档通过；GLM-5.2 在 sanitize-git-repo 上验证动作更多，却顺手改写仓库历史删掉了验收必需的 commit。

### 3.5 发现四：按任务配额分配 effort——朴素阶梯打赢固定高档

作者比较四种策略：oracle 路由（事后选最便宜的成功档位，理论下界）、self-routing（模型看任务描述自选档位）、**naïve laddering（最低档起步，仅在外部验证失败后升到最高档重试，重试两次都计费）**、随机分配。

- self-routing 不可靠：模型无法从任务描述预判难度，表现与随机分配无异。
- **naïve laddering 在全部 8 模型 × 4 基准上匹配或超过固定最高档的成功率**，同时省成本：

| 指标（laddering vs 固定最高档） | 结果 |
|------|------|
| AIME / GPQA / 修正 SWE-Bench Pro | 模型中位成本省 25.3% / 41.5% / 15.5%（含重试双倍计费） |
| Terminal-Bench，GPT-5.6-sol | 成功率 83.0% → 88.6%，成本 −17.4% |
| Terminal-Bench，Claude Sonnet 5 | 76.1% → 83.0%，成本 −8.7% |
| Terminal-Bench，Kimi K3 | 73.0% → 84.3%，成本 −30.5% |

作者给出计入用户等待时间的全成本公式：

$$C_{full}(i,e,m) = C_{API}(i,e,m) + \frac{w \cdot N_{out}(i,e;m)}{3600 \cdot r_m}$$

其中 $N_{out}$ 为全部生成 token（含推理），$r_m$ 为输出吞吐（token/s），$w = \$33.54$ 为美国平均时薪。**等待时间在所有档位下占总成本 80% 以上**。计入后 laddering 优势更明显：GPT-5.6-terra 在 Terminal-Bench 上全成本比固定 xhigh 省 19.5%，而纯 API 账单口径只省 4.8%——因为 laddering 虽然可能多付 API 费（缓存不跨次共享），但总生成 token 更少、等待更短。

## 四、实验结果与分析

综合上面各表，核心结论可压缩成三条：

1. **高档位不是超集**：8/8 模型在 agent 基准上存在回退集，聚合准确率是"两个不相交集合之差"，报 net gain 的惯例藏住了被放弃的成功。
2. **成本随 effort 单调涨、精度不随 effort 单调涨**：$s_{all}$ 上最高 42 倍的成本差距换来零额外成功；none 档也不便宜（×4.58）。
3. **动态配额 > 一档定终身**：阶梯策略以"低档保底 + 验证失败才升档"的设计，天然保留低档全部成功、只在值得处付高价，在所有配置上 Pareto 改进。

作者同时反复强调两个诚实的限定：agent 任务单次运行的回退里含采样噪声（附录 DeepSWE 4 次重跑佐证现象量级稳定）；laddering 依赖可靠的**外部正确性检查**，很多部署并不具备，且每次升级要付完整二次执行的钱，它是权宜之计而非终局方案。

## 五、与 AI 基础设施的关联

这篇论文对 AI Infra（推理服务与资源调度）的启发相当直接：

1. **推理服务的容量与成本规划**：effort 档位现在是用户侧控制推理开销的主杠杆。服务商做容量规划、SLA 定价、批处理调度时，不能假设 effort 只线性改变单请求算力——它同时改变轨迹长度、input token 重处理量和端到端延迟。本文给出的乘数效应（2.5×–42×）和"none 档反而更贵"的发现，直接推翻"低 effort = 低负载"的朴素调度假设。
2. **动态 test-time compute 分配 = 调度问题**：oracle 路由与 laddering 之间的差距，本质是一个在线资源分配问题——何时给一个请求追加推理预算。这启发推理系统把 effort 控制做成运行时可调（执行中遇到真实难度再加码），而不是请求级一次性旋钮；与早停、投机解码、预算感知路由等机制可以在同一框架下调度。
3. **计费与可观测性（MLOps 议题）**：隐藏推理 token 被计费且不可审计，构成道德风险。论文呼吁 provider 让推理计费可验证、明示每个档位到底控制什么（token 预算？轨迹长度？行为？）。对做 LLMOps/网关的团队，这意味着需要 per-effort 的成本归因、验证信号采集和审计日志。
4. **延迟感知的成本核算**：等待时间占全成本 80%+，而 API 账单不追踪延迟。任何 agent 平台的 ROI 分析若只算 token 钱，会系统性误判配置优劣；$C_{full}$ 公式提供了一个可直接套用的核算框架（$w$、$r_m$ 参数化，换成自己的时薪和吞吐即可）。
5. **评测基础设施的泄漏治理**：SWE-Bench Pro 的 git 历史泄漏案例是给 benchmark 运维的警示——agent 越强越会"抄近道"，评测环境必须做信息隔离（删历史、限网络），否则高档位的"提升"是评测器被攻破的假象。

## 六、总结与启发

**亮点**：选题角度极好——把一个用户天天要拍脑袋的决定（开多大 effort）第一次做成了任务粒度的反事实审计；"信用商品"的经济学框架让现象有了清晰的解释结构；控制变量干净（同任务同 prompt 同 harness），成本核算把 token 和美元解耦；行为分析（Act·ONOMY 标注）把"多想"拆解成"多验证 + 多检索"，解释了成本为何不随难度收缩；修正版 SWE-Bench Pro 的构造本身就是可复用的评测卫生实践。结论落地性极强：laddering 是今天就能用的省钱策略。

**不足**：agent 任务每档单次运行，回退集里混有采样噪声（作者已声明并用附录补救，但任务级统计功效仍受限）；未覆盖 max 档（太贵）和各家未公开的 effort 内部实现差异（gpt-oss 用提示词关键词、Qwen3 截断思维、DeepSeek-V4 蒸馏专家、Kimi K3 长度惩罚——机制不同，"同名档位"未必同质）；laddering 依赖外部正确性检查，对开放式任务（写作、设计）不适用；$w$ 用美国平均时薪估算等待成本，个体差异大。

**对后续研究的启发**：最大的开放问题是**执行中的动态 effort 自适应**——模型在运行时感知到真实难度才追加算力，这需要把 effort 从"命名档位"变成"受控量"（明确的 token 预算/轨迹预算/行为预算）；其次是让推理计费可验证（provider 侧的透明度机制设计）；再者是把"验证信号的可靠性"纳入 effort 路由的决策回路——laddering 的价值上限取决于外部检查器的质量，这把评测器设计和算力调度连成了同一个问题。

一句话总结：**reasoning effort 不是有序旋钮，是信用商品；默认开最大档既不省钱也不保证最好，"最低档起步、验证失败再升档"今天就能替你省钱，而真正的答案是让系统在运行中按需买推理。**
