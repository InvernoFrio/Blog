## 研究背景与动机

具身智能体（Embodied Agents）通常由**感知、记忆、规划和动作**四大模块手设计组合而成。这种模块化设计模式在视觉语言导航（VLN）、具身问答（EQA）和语言条件操纵等任务中广泛使用。与端到端策略不同，具身智能体的架构是**显式的**——信息如何流动、模块如何连接，都可以被编辑和修改。

但这种显式结构也带来了一个根本问题：**架构设计空间巨大，但设计过程仍然依赖研究者的直觉**。每个智能体都需要手工确定传感器抽象、地图表示、记忆状态、提示结构、规划器拓扑、模型调用方式等。随着基础模型和具身工具不断增多，可能的架构组合空间增长速度远超人工迭代能覆盖的范围。

**Agent Architecture Search（AAS）** 在文本域智能体中已经取得进展（如 ADAS、AFlow、AgentSquare），能够自动优化 LLM 智能体的工作流。但从文本域迁移到具身域并非直接转移：

1. 文本域 AAS 操作的是**廉价、无状态**的 LLM 调用，有成熟的可组合原语（如 CoT、辩论、自精炼）
2. 具身智能体需要与**有状态模拟器**交互，产生**带噪声的多回合评估**，依赖包含观测、动作、工具调用的长执行轨迹
3. 具身域没有一套小而通用的可组合推理原语——每个任务的感知、状态和动作接口都是任务特定的

本文的核心问题是：**AAS 能否从文本域成功迁移到具身域？这种迁移面临什么新约束？**

## 核心方法与创新点

### 整体框架：方法种子化架构搜索

本文采用**方法种子化（method-seeded）** 的 AAS 设置。不是从零组装智能体，而是以已发表的具身智能体架构（如 MapGPT、SmartWay、ExploreEQA、VoxPoser）为起点，搜索其附近的图级修改。

形式化表述：令 $\mathcal{C}$ 为可执行的具身智能体图空间，每个候选 $c \in \mathcal{C}$ 有适应度 $f(c)$（由多回合模拟器评估的成功率衡量）。给定种子执行器 $c_0$ 和预算 $B$，AAS 变体生成轨迹 $\{c_t\}_{t=0}^B$，返回最优候选 $\arg\max_{t \leq B} f(c_t)$。不同变体的差异在于**搜索策略**——即从轨迹产生 $c_{t+1}$ 的转移规则。

### 创新点一：AgentCanvas — 类型化图运行时

AgentCanvas 是一个**类型化节点-连线图运行时**，将具身执行器表示为可编辑的 JSON 图，底层由 Python 节点模块支撑。

**关键设计：**
- **类型化端口**：节点暴露类型化输入-输出端口，图编辑（添加边、替换子图）在执行前进行类型兼容性检查，避免在昂贵的模拟器 rollout 上浪费计算
- **执行器日志**：每次 rollout 都会记录节点的外部输入输出和内部"面包屑"（planner 决策、提示、工具调用、自报告），这些 episode 级记录将候选编辑与下游行为关联
- **可扩展性**：模拟器依赖的节点在 worker 间复制，共享的基础模型节点作为单例服务批量处理请求，支持多回合评估而无需为每个 worker 重新加载模型权重

### 创新点二：KDLoop — 编码智能体搜索流程

KDLoop 是一个**编码智能体编排的搜索流程**，每个迭代经历五个阶段：

1. **THINK**：分析当前执行器的性能和日志，提出图编辑假设
2. **CRITIC**：评估提议的编辑是否合理，是否有潜在风险（如信息泄露）
3. **EXPERIMENT**：应用编辑，运行模拟器评估
4. **DISTILL**：从实验结果中提取经验教训
5. **REFLECT**（触发式）：当搜索停滞时触发深度反思，跳出局部编辑盆地

与 ADAS（单次 LLM 补全生成候选）和 AFlow（基于工作流模板的搜索）不同，KDLoop 使用完整的编码智能体来编辑多文件具身智能体代码，每个 patch 都需要保持与模拟器 API、模块接口和诊断日志的兼容性。

### 三种 AAS 变体对比

| 变体 | 候选生成方式 | 特点 |
|------|-------------|------|
| ADAS | 单次 LLM 补全 | 最简单，但可能遗漏复杂编辑 |
| AFlow | 工作流模板搜索 | 结构化，但受限于模板空间 |
| KDLoop | 编码智能体迭代 | 最灵活，支持复杂多文件编辑 |

## 实验结果与分析

### 实验设置

- **任务类型**：视觉语言导航（VLN）、具身问答（EQA）、语言条件操纵
- **种子执行器**：MapGPT、SmartWay、ExploreEQA、VoxPoser（4个已发表系统）
- **评估矩阵**：3种 AAS 变体 × 4个种子执行器 = 12组实验

### 核心发现

**1. 架构搜索确实能带来可部署的提升**

多个搜索得到的图在种子基线上获得了**确认的成功率提升**（ΔSR）。这些提升表明架构级搜索能产生功能性的行为改变，而非仅仅是表面的工作流重组——这反驳了近期对文本域 AAS 的批评。

**2. 一个看似高分的候选被拒绝为"泄露型"**

在评估中，一个表面上表现优异的候选被识别为存在信息泄露（leak-bearing），说明 AAS 需要可靠的验证机制来过滤虚假提升。

**3. 具身 AAS 面临三大约束（文本域不显著的）**

- **评估噪声（Rollout Noise）**：模拟器 rollout 的随机性可能掩盖图编辑的效果，使得优化信号模糊
- **局部编辑盆地（Local Edit Basins）**：搜索可能反复利用同一类局部修改，而非发现质性不同的机制
- **部分信用分配（Partial Credit Assignment）**：即使有详细的 episode 日志，智能体也难以系统性地将最终结果归因到具体的架构修改

### KDLoop 的表现

KDLoop 在三种变体中表现最优，其触发式 REFLECT 机制在搜索停滞时能有效跳出局部最优。但即使是最优变体，也无法完全克服上述三大约束。

## 与智能体认知模块的关联

这篇论文对智能体认知架构研究有多方面启发：

### 1. 模块化架构的可搜索性

本文证明了**感知-记忆-规划-动作**模块的组合空间是可以被系统性搜索的。这对智能体认知架构设计意味着：与其依赖研究者的直觉选择模块组合，不如让搜索算法来探索设计空间。这与我们之前讨论的"认知架构应该是可配置的而非固定的"观点一致。

### 2. 记忆模块的架构位置

在 AgentCanvas 的图表示中，记忆模块的位置（何时写入、何时读取、如何压缩）都是可编辑的图结构。这暗示了**记忆注入策略**可能比记忆内容本身更重要——与昨天讨论的"主动记忆干预"论文形成有趣呼应。

### 3. 从手工设计到自动设计的范式转移

本文的核心贡献不仅是具体的技术方案，更是提出了一种**范式**：智能体的认知架构设计应该是一个可优化的目标，而非固定的工程选择。这与神经架构搜索（NAS）在深度学习中的角色类似——AAS 可能成为智能体开发的标准工具。

### 4. 局限性的启示

三大约束（评估噪声、局部盆地、部分信用分配）本质上反映了**具身智能体评估的困难性**。这提示我们：在设计智能体认知架构时，不仅要考虑架构本身的表达能力，还要考虑评估信号的质量。

## 总结与启发

### 亮点

1. **首次系统性评估** AAS 从文本域到具身域的迁移，填补了重要空白
2. **AgentCanvas 的类型化图设计**优雅地将具身智能体表示为可编辑、可执行、可日志化的程序
3. **KDLoop 的编码智能体搜索**比单次 LLM 补全更适合复杂的多文件编辑
4. **诚实的局限性分析**：不仅报告成功案例，还深入分析了具身 AAS 面临的三大约束

### 不足

1. **实验规模有限**：仅 4 个种子执行器 × 3 种任务类型，泛化性有待验证
2. **评估成本高**：每次候选评估都需要多回合模拟器 rollout，搜索效率是瓶颈
3. **缺乏理论保证**：搜索是否收敛到全局最优？局部盆地的结构是什么？这些问题未被回答
4. **模块化假设的局限**：是否所有具身智能体都能被有效表示为节点-连线图？某些端到端组件可能难以模块化

### 启发

这篇论文最重要的启发是：**智能体架构设计应该被视为一个可优化的问题，而非固定的工程选择**。随着基础模型和工具的增多，架构搜索可能成为智能体开发的标准流程。但要实现这一愿景，我们需要更好的评估信号、更高效的搜索策略，以及对架构空间结构的更深入理解。

对于智能体研究者来说，AgentCanvas 的类型化图表示是一个值得借鉴的设计模式——它使得架构的可编辑性和可评估性成为一等公民。
