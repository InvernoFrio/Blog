## 二、研究背景与动机

智能体 LLM 的开发离不开三类批式工作流：**基准评测**（benchmark evaluation）、**合成数据生成**（synthetic-data generation）和 **RL rollout**。它们的共同特点是：一批样本（sample）各自执行一条多轮"推理 ↔ 环境交互"交替的轨迹（trajectory），下游阶段要等整批跑完才能开始。因此真正决定开发迭代速度的不是传统服务里关心的 TTFT/TPOT 等请求级延迟，而是**批完成时间（batch makespan）**——最后一个样本结束所需的时间。

现有系统在这类负载上有三个具体痛点：

1. **混合模型的缓存分配靠拍脑袋**。Ling-3.0-Flash、Qwen3.8-Max、Kimi K3 这类混合架构（如 MLA + KDA）同时需要 KV cache 和循环状态（recurrent state）才能跨轮复用缓存。KV cache 需求随上下文增长，循环状态是每轨迹固定大小。SGLang 在共享显存预算里给两者各开一个池子，默认比例一旦不匹配负载特征，就会出现"一个池子爆了、另一个还空着"，能同时驻留缓存的轨迹数被压低。
2. **多 worker 下亲和与负载难两兼**。同一轨迹的请求发到同一 worker 利于缓存复用，但严格亲和会把负载堆到个别 worker；即便 worker 上有可复用状态，请求排队久了状态也被淘汰了。而 agent 上下文动辄很长，靠 token 前缀匹配找复用机会的开销也很大。
3. **环境侧资源受限时两个阶段互相拖累**。MCP-Atlas、τ³-bench 这类任务依赖外部 MCP 服务/CPU 预算，环境并发能力往往低于推理服务。用单一的样本并发上限同时控制准入和环境执行：调高会压垮环境，调低又让推理 worker 饿着。更糟的是，长轨迹被反复插队，其后续阶段被推到批次末尾，形成漫长的**完成尾部（completion tail）**。

## 三、核心方法与创新点

论文在 SGLang 上实现了一套"推理侧优化 + 推理-环境协同"的组合拳，共五个组件：

### 1. 工作负载感知的混合缓存分配（Workload-Aware Hybrid-Cache Allocation）

部署前用目标负载的轨迹画像（token 足迹、轨迹数）解析地求出 KV cache 与循环状态池的平衡比例 r^bal，以及参考样本并发 C_ref = ⌊C(r^bal; D)⌋，使两个池子的"可驻留轨迹数"相等，从而最大化跨轮复用的轨迹数量；运行期分配固定不变。直觉上：每条轨迹只保留一份最新循环状态（它已概括整条前缀），因此循环状态需求与轮数无关，而 KV cache 随轮数增长——r^bal 就是让两类资源同时见底的那个配比。

### 2. 负载有界一致哈希路由（LBCH）

用**轨迹标签**（trajectory label）作为廉价的亲和键替代昂贵的 token 前缀匹配：同一轨迹的请求哈希到同一 worker 保住跨轮复用，同时对 worker 负载设界，超过阈值就溢出到次选 worker，避免热点。

### 3. 路由前缀调度（Routing-Prefix, RP）

worker 内的本地调度策略。同样用轨迹标签先粗筛等待队列，优先放行"最近刚被服务过的轨迹"的请求，让它们趁缓存还没被淘汰就完成复用；只有需要更精细判断时才去查前缀缓存树，调度开销低。

### 4. 容量解耦（Capacity Separation）

把样本准入上限 C_S 和环境执行上限 C_E 拆开独立配置：C_S 调大让推理与环境阶段在更多轨迹间重叠、提高 GPU 利用率，C_E 保护环境不被打爆。

### 5. 链推进动作调度（Chain-Advancing Action Scheduling, CAAS）

环境作业排队时，不按 FCFS，而是**用观测到的轨迹进度优先调度"可能更长"的轨迹的作业**——不需要预知剩余长度。长链的后续阶段被尽早暴露出来，避免它们拖到批次尾部成为收尾瓶颈。一个配套的评估工具是**受控回放（controlled replay）**：真实推理 + 录制的环境响应与时长，用于对单个优化做消融。

批次尾部用 L_p = t_100 − t_{100−p} 度量（如 p=5 表示最后 5% 任务的完成区间）。

## 四、实验结果与分析

### 实验设置

- 模型：Ling-3.0-Flash（124B 总参/5.1B 激活，2×TP4、8×H20）、Ling-3.1-Flash（560B 总参/25B 激活，2×TP8、16×H20）
- 基准：BFCL、SWE-bench Multilingual、WideSearch、MCP-Atlas
- 对照：Baseline（默认缓存比例 + FCFS + 缓存感知路由）、Baseline-2（与 Opt 同并发但保留基线缓存/调度）、Opt（容量模型指引 + RP + LBCH，MCP-Atlas 再加容量解耦与 CAAS）
- 每配置 3 次运行取均值，makespan 含全部样本与重试时间

### 推理侧在线结果（Table 2）

| 模型 | 负载 | 配置 | Makespan (min) | 缓存复用率 (%) | 分数 |
|------|------|------|---------------:|---------------:|-----:|
| 3.0 | BFCL | Baseline | 68.4 | 84.2 | 73.0 |
| 3.0 | BFCL | Opt | **49.2** | 84.5 | 75.65 |
| 3.0 | SWE | Baseline-1 | 166.9 | 98.3 | 72.4 |
| 3.0 | SWE | Baseline-2（同并发） | 197.7 | 87.5 | 71.3 |
| 3.0 | SWE | Opt | **149.5** | 98.6 | 72.6 |
| 3.0 | WideSearch | Baseline | 186.7 | 79.9 | 73.6 |
| 3.0 | WideSearch | Opt | **116.7** | 81.7 | 72.7 |
| 3.1 | SWE | Baseline-1 | 234.1 | 98.2 | 87.16 |
| 3.1 | SWE | Baseline-2（同并发） | 304.1 | 80.4 | 86.0 |
| 3.1 | SWE | Opt | **185.1** | 98.3 | 88.33 |
| 3.1 | WideSearch | Baseline | 459.9 | 83.2 | 78.6 |
| 3.1 | WideSearch | Opt | **359.1** | 80.7 | 78.1 |

关键解读：

- 相对基线，Ling-3.0-Flash 上 makespan 降 28.1%（BFCL）、10.4%（SWE）、37.5%（WideSearch）；Ling-3.1-Flash 上降 20.9%（SWE）、21.9%（WideSearch）。
- **Baseline-2 对照非常有说服力**：同并发下，基线缓存/调度的复用率掉到 80–88%，Opt 把复用率拉回 98% 以上、新 prefill token 减少 88.9%/91.5%，makespan 比 Baseline-2 短 24.4%/39.1%——证明收益来自"缓存分配 + 调度"而非单纯堆并发。
- 缓存比例与并发必须**联合选择**：SWE 上并发从 147 加到 157、BFCL 从 644 加到 859 时，新 prefill 工作量暴涨 3–11 倍，输出吞吐反而下降；模型推导的 (r^bal, C_ref) 工作点已接近网格搜索的最优值。
- 评分与基线持平或略优（73.0→75.65、87.16→88.33），加速不以质量为代价。

### 环境协同结果（受控回放 + 在线）

- **容量解耦**：把准入从统一上限提到 C_S=10 就让 makespan 降约 1/3；继续提到 25/50 收益递减（环境执行上限约束了后续推理工作的释放）。
- **CAAS（回放）**：C_E=3/5 时 makespan 再降 1.9%/3.5%，最后 5% 尾部时长缩短 19.0%/21.4%。
- **MCP-Atlas 在线（Table 3，500 任务 × 3 次）**：

| 模型 | 配置 | Makespan (min) | 平均在飞推理请求 | L5 (min) | 分数 |
|------|------|---------------:|----------------:|---------:|-----:|
| 3.0 | Baseline | 466.1 | 1.2 | 38.9 | 65.5 |
| 3.0 | Opt-FCFS | 168.2 | 7.3 | 67.6 | 66.6 |
| 3.0 | Opt-CAAS | **163.0** | 7.9 | 66.0 | 65.6 |
| 3.1 | Baseline | 333.5 | 1.6 | 26.1 | 81.0 |
| 3.1 | Opt-FCFS | 140.5 | 12.5 | 49.8 | 80.9 |
| 3.1 | Opt-CAAS | **128.5** | 11.5 | 35.3 | 81.3 |

相对统一准入基线，makespan 降 63.9%（3.0）/57.9%（3.1）；CAAS 进一步降 3.1%/8.5%，L5/L10 尾部在 3.1 上缩短约 29%。一个有意思的细节：Opt-CAAS 的 L5 反而比基线长（66.0 vs 38.9），因为放宽准入后"最后完成的 25 个任务"平均 27.9 轮，而基线里垫底的多是晚准入的短任务（10.1 轮）——**跨准入策略比较时不能只看 L5**，这也是论文给出的诚实告诫。

## 五、与 AI 基础设施的关联

这篇是典型的 **AI4AIInfra** 论文，对 LLM 推理服务与训练系统的启发很实在：

1. **目标函数要跟着工作流走**：在线服务优化 TTFT/TPOT，但 RL rollout/评测/合成数据这类批任务的目标是 makespan。RL 后训练系统（如 Agentic RL 训练平台）应把"批次尾部"作为一等公民指标——尾部长短决定一个训练迭代的墙钟时间。
2. **混合架构时代的缓存管理是显存调度问题**：MLA+KDA/SSM 类混合模型的 KV cache 与循环状态异构、增长规律不同，静态配比 + 参考并发这类"部署期画像、运行期固定"的做法简单有效，是 vLLM/SGLang 缓存池管理可以借鉴的方向。
3. **轨迹标签是比前缀匹配便宜得多的调度信号**：用 O(1) 的标签替代长上下文前缀树查询做路由亲和与调度优先级，对超长 agent 上下文尤其划算。这提示调度器设计可以从"内容感知"退化到"身份感知"，用更少的信息量拿到大部分收益。
4. **准入控制与执行控制解耦**是经典的排队论智慧在 LLM 系统里的再验证：多级并发上限（样本准入 vs 环境执行）+ 以"观测进度"为优先级的动作调度，直接对应数据中心调度里"已知长度的 SRPT"的无先验版本。对受限外部资源（工具 API 配额、沙箱 CPU）的 agent 服务尤其适用。
5. **受控回放是系统消融的好范式**：真实推理 + 录制环境响应/时长，既保真又可控，值得所有做 agent serving 研究的团队抄。

## 六、总结与启发

**亮点**：问题定义精准（makespan 而非请求延迟），五个组件从显存分配、路由、调度到准入/动作调度形成完整闭环；实验设计扎实——Baseline-2 同并发对照、受控回放消融、跨模型规模（124B→560B）验证，并且已经在 Ling-3.x 的真实开发流程中落地，是"研究即生产"的典型样本。

**不足**：缓存分配是部署期静态的，负载漂移时需要重配；CAAS 依赖"已观测进度"启发式，对轨迹长度分布极端的任务可能失准；实验全部基于混合架构 + SGLang，对纯 dense 模型和其他引擎的泛化未验证。

**启发**：做 Agentic RL 基础设施的同学值得记住三句话——缓存比例和并发要联合调、调度信号可以很便宜、长链优先推进能砍掉批次尾部。下次被 RL rollout 慢折磨时，先看看你的系统里 C_S 和 C_E 是不是还绑在一起。
