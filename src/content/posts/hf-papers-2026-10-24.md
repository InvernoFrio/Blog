今天从 HF Papers 的 AI4AIInfra 候选里选中这一篇，因为它正好卡在「算法很热、系统跟不上」的断层上：token 级路由的算法论文这两年层出不穷，但几乎没有一篇能把它真正跑在生产级服务系统上拿到该有的吞吐收益——这篇就是来填这个坑的，而且是 NeurIPS 2026 接收、带开源代码的系统工作。

## 二、研究背景与动机

**模型路由（model routing）已经是生产系统的标配。** ChatGPT、Cursor 都会按难度或话题把用户 query 分发给不同后端模型，学术界的 RouteLLM 也证明 query 级路由能用更低的成本逼近强模型。但这类路由是**粗粒度**的：一个请求一旦绑定模型，整个回答都由它生成，直到下一轮才可能换。

**细粒度的 token 级路由收益更大。** 单个 query 内部的生成难度起伏剧烈——比如 R2R 只需把 5% 的 token 路由给 32B 大模型、其余交给 1.5B 小模型，就能匹配 32B 单模型的质量；而 query 级路由要达到同等质量得把约 40% 的请求整个交给大模型。此外，token 级路由还能让专长互补的多个模型在同一回答里协作，质量超过任何单一模型，并提供连续的成本-质量权衡曲线，而不是粗粒度路由那几个离散档位。

**但是，现有服务系统根本跑不动 token 级路由。** vLLM、SGLang 都按「单 LLM、所有活跃请求每步同步」设计，token 级路由让目标模型每个解码步都可能切换，直接打破这个假设，带来三个问题：

1. **步调失同步（step desynchronization）**：不同模型单步延迟差异巨大（实测 SLM 6.0ms vs LLM 27.9ms）。如果强行同步，每一步都要等最慢的模型，快模型全程空转；
2. **批量准入延迟（batch admission delay）**：路由导致频繁换模型，被路由的请求到达目标模型时，对方往往正在跑上一批，只能干等下一批，产生气泡、把 batch 切碎；
3. **实现复杂度**：现有系统没有暴露「每步路由决策」的编程接口，在里面实现 token 级路由要大改代码库，还得和 continuous batching、prefix caching 等紧耦合特性小心翼翼地协调。

作者的判断很清晰：这不是再写一个路由算法能解决的，需要一个**专门的服务系统**。

## 三、核心方法与创新点

TokenRouter 的总设计原则是一句话：**请求中心编程（request-centric programming），模型中心执行（model-centric execution）**。开发者只按「一个请求怎么在多个模型间流动」来写路由算法，异步调度、批量、跨模型状态传递全部由运行时接管。

### 3.1 route-send-receive 编程接口

作者抽象了所有 token 级路由算法共有的生命周期：

```
receive → decode → route → send → peer receive → peer decode → peer route → ⋯
```

开发者只需填三个函数：

- **route(result)**：每个解码步后调用，根据前向结果（hidden states、next-token logits、采样 token）为 batch 中每个请求决定目的地——0 表示留在本地，非 0 指向对端模型；
- **send(req)**：被委派时构造 PeerReq 消息，携带请求 ID、对端没见过的 token 后缀、状态字段和算法自定义字段，并附位置锚点 `req.loc`，让接收方知道该从哪里续、回传最小后缀；
- **receive(peer_req)**：把 PeerReq 转成本地请求格式继续解码，默认「全盘接受」，算法有特殊交接语义时才需重写。

以 R-Stitch 的小模型侧为例，route 就是把归一化熵超过阈值 τ 的 token 发给大模型，send 只传对端未见过的后缀并**排除**那个不确定 token（让大模型从该位置重新生成），十几行代码就表达完了。论文验证的 5 种算法——CITER（置信度触发）、R2R（预测分歧触发）、R-Stitch（熵阈值对称切换）、Co-LLM（deferral 触发）、ME（≥2 模型按集成权重逐步选择）——全部能用这三个函数表达。

### 3.2 异步执行：三解耦循环 + handoff-resume

标准服务系统有两个异步循环：客户端-服务端循环（准入/流式输出）和解码循环（调度/模型执行）。TokenRouter 加了**第三个解耦的模型间循环**，负责在 subserver 之间收发 peer request。效果是：被路由的请求可以「离开」本地 batch 去对端模型跑，本地其余请求按自己的节奏继续；等 peer request 回来，调度器再把它接回本地 batch。各 subserver 独立推进，彻底消除全局同步。

跨模型切换的开销靠 **handoff-resume 机制**压掉：朴素做法是把返回的请求当新请求，重新做 prefix matching 和 KV-cache 分配。TokenRouter 引入 **pending 状态**（介于 running 和 finished 之间）：交接时标记 pending，调度器跳过它但保留全部服务状态；恢复时切回 running，把新 token 追加上去、像从没离开过一样重新入 batch。跨模型交接退化为「一次 token 追加」。对照实验的延迟分解显示这个优化多关键——Std. Serving 基线每个解码步里 prefix matching 占 20.9%、锁 cache 节点 17.5%、更新 RadixCache 32.6%，**真正的 SLM 推理只占 4.2%**。

### 3.3 延迟批处理调度器（delayed batching）

异步化之后，每个 subserver 仍要面对稀疏、不规则的路由 token 到达。延迟批处理的思路：**刻意等一小会儿**，让同模型的请求攒够 B 个再一起开批——先到的请求多等一点，但后来的请求等待大幅缩短，平均批量准入延迟反而下降。B 太小失去聚合意义，太大会把请求饿死在队列里（甚至死锁，论文给的可行性条件是 $\sum_i (B_i - 1) < N$）。

关键的 B\* 怎么定？论文建立了一个**离散时间马尔可夫链（DTMC）吞吐模型**：

- 系统状态 $\mathbf{s} := (k_0, b_0, r_0, \dots, k_{M-1}, b_{M-1}, r_{M-1})$：每个模型的排队数、在跑 batch 大小、剩余执行时间；
- 输入参数：并发数 N、路由转移矩阵 $\mathbf{P} = [p_{ij}]$（一步后从模型 i 路由到 j 的概率）、token 提交矩阵 $\mathbf{C} = [c_{ij}]$、各模型单步延迟 $L_i$；
- 在每个「批完成事件」上定义状态转移（路由结果服从多项式分布），求解平稳分布 $\boldsymbol{\pi}_{\mathbf{B}}$，得到稳态吞吐：

$$T(\mathbf{B}) = \frac{\sum_{\mathbf{s}} \sum_{i \in \mathcal{A}(\mathbf{s})} \sum_j \pi_{\mathbf{B}}(\mathbf{s})\, b_i\, c_{ij}\, p_{ij}}{\sum_{\mathbf{s}} \pi_{\mathbf{B}}(\mathbf{s})\, \tau(\mathbf{s})}$$

最后在有限可行集上枚举 $B^\star = \arg\max T(\mathbf{B})$。用 R2R 实测参数（p=0.35，SLM 6.0ms、LLM 27.9ms）验证：模型预测的吞吐趋势与实测吻合，且**每个并发度下预测的最优阈值都恰好落在实测最优上**——不是拟合出来的，是解析模型直接指对了。

### 3.4 工程细节（打破单模型假设的补丁）

- **KV-cache 联合分配**：多个模型共居同一 GPU 时，按各自权重占用和 per-token KV 大小，在共享显存预算内算出最大公共 KV 容量自动分账，免去手工预留；
- **extend 模式 CUDA graph**：路由交接回来的请求都走 extend 而非 decode，所以对一段可配置范围的 extend batch 尺寸捕获 CUDA graph，主流路径免掉 kernel 启动开销；
- **进程内 router**：route 函数每个前向都要跑，放独立进程等于每 token 一次 IPC；改为与调度器同 GPU 同进程，变成进程内张量运算；
- **全局状态跟踪**：B\* 依赖全局活跃请求数，靠 peer 消息通道捎带状态通告保持各 subserver 一致，不引入中心协调器。

## 四、实验结果与分析

**设置**：8×A100-80G；两模型算法小模型 1 GPU、大模型 TP=2，经 CUDA MPS 共享；5 种路由算法 × 3 类负载（AIME2024 短输入短输出 2,048 / 高难度长输出 8,192 / SWE-Smith 多轮 agentic 约 8K 入 1K 出）× 并发 1-16。基线为各算法官方实现和自建的 Std. Serving（每模型一个 SGLang server + 外部逐 token 转发）。

**总体结果**：15 个算法-负载组合上吞吐比更强基线高 **2.01–64.15×**，端到端延迟比 Std. Serving 低 2.03–63.64×；在各算法「原始设置」下比官方实现吞吐高 2.73–21.97×、延迟低 2.78–21.61×。

| R2R | LLM-only | 145.30 | 0.13 | 411.98 |

| 并行策略 | LLM 的 TP 从 1→2 提升 22.8–40.6%，SLM 的 TP 加不加几乎没差（<1%）——资源优先给大模型 |

## 五、与 AI 基础设施的关联

这篇是典型的「AI4AIInfra」论文——用系统方法放大算法收益，对 AI Infra 研究有多层启发：

1. **LLM 推理服务**：多模型协作（路由、推测解码、MoE 专家切换）正在成为常态，而主流引擎还停留在单模型假设。TokenRouter 的「每模型自治 subserver + 异步 peer 消息」给出了一种可扩展的多模型服务范式，对外仍是单端点协议、可作 drop-in 替换，这个兼容性设计值得所有推理框架抄。
2. **调度与资源调度**：延迟批处理本质上是「用有界等待换更大 batch」，和 disaggregated prefill/decode、混合负载调度里的 chunk 重排是同一族权衡。更进一步，B\* 由解析吞吐模型直接给出而非网格搜索——**调度超参可以被建模推导**，这对在线自适应调度（按流量动态调 B）是现成的理论工具。
3. **状态管理**：handoff-resume + pending 状态说明「请求状态机」应当独立于「模型实例」存在。对照数据（推理只占每步 4.2% 时间）提醒我们：在多模型/分布式场景里，缓存簿记、锁、前缀匹配这些「非推理开销」才是吞吐杀手，值得在 profiling 时优先盯。
4. **编译优化与运行时**：extend 模式 CUDA graph、进程内 router、联合 KV 预算，都是「执行形态改变后要重新打破旧优化假设」的例子——做 AI 编译器/运行时的人可以从中提炼 checklist。
5. **对 agentic 负载的意义**：实验包含 SWE-Smith 多轮 agentic 轨迹（约 8K 输入），token 级路由 + 长上下文 + 高并发正是 agent 服务的真实形态，结论对 agent serving 平台的容量规划直接可用。

## 六、总结与启发

**亮点**：

- 选题精准：token 级路由算法收益早已被证明，但没人认真做过「怎么服务它」，这篇把 2.01–64.15× 的系统收益补齐，让算法收益真正落地；
- 「请求中心编程、模型中心执行」是漂亮的抽象：开发者十几行实现一个路由算法，性能问题由运行时兜底，兼顾了易用性和效率；
- 调度超参由 DTMC 吞吐模型解析求得并被实测验证，是系统论文里少见的「理论指导实现」的干净闭环；
- 评测扎实：5 算法 × 3 负载 × 多模型对 × 多部署形态（重叠/非重叠/跨节点），并给出完整的增益分解和延迟分解。

**不足与开放问题**：

- 吞吐模型假设路由概率平稳、请求间独立，长尾负载或自适应路由（概率随内容实时变化）下 B\* 是否仍然最优，需要在线重估机制；
- B\* 是离线按给定并发 N 标定的，生产流量并发波动时如何在线自适应调整阈值没有展开；
- 模型对实验最大到 32B 级，对数百 B 的 MoE 大模型或专家并行场景的适用性待验证；
- 跨节点仅测了 RoCE 3.7GB/s 一种网络，更高延迟网络下 peer 消息开销的影响未量化。

**对后续研究的启发**：多模型协作服务会越来越普遍（路由、推测解码、speculative + routing 混合、MoE 内部切换），「模型中心 subserver + 请求级状态保持 + 模型推导的调度参数」这套组合拳可以直接迁移。反过来，token 级路由算法的设计者也该把「交接成本」纳入目标函数——send 传多长的后缀、何时切回，都是可以和系统联合优化的自由度。
