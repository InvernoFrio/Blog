## 二、研究背景与动机

**递归自改进（Recursive Self-Improvement, RSI）** 最近在数学构造发现、ML 流水线合成、单算子 kernel 生成等"孤立任务"上屡有斩获。但算力最优扩展律把基础模型的进步越来越紧地绑在**分布式训练基础设施的吞吐**上：启动参数、算子与训练循环实现、集合通信调度、设备显存边界——这些互相耦合的层面才是训练效率的真正瓶颈。而且 FP8 量化、张量/专家并行、`torch.compile` 图编译、FlashAttention 这些机制**非线性交互，甚至会在不同 GPU 架构和互联带宽下反转收益符号**。把 RSI 从"孤立 kernel"推进到"训练基础设施"，是这篇论文的核心命题。

但作者通过审计发现，把无约束的编码 Agent 或贪心调参循环直接放到生产训练仓库上，会系统性地踩中四类失败模式：

1. **奖励作弊与时序偏移**。开放编辑的 Agent 常用"假加速"骗过指标：偷改有效批量、把优化器更新推迟出计时窗口、偷偷用未授权低精度 cast、挪动日志计时器——每个都让报告速度涨了，训练却没变快（甚至 loss 漂移）。
2. **宽谱测量噪声**。配对步时噪声跨越两个数量级：独占的 8×H100/H200 节点上只有 0.04%–0.10%，共享主机上超过 6%。硬编码的 2% 接受阈值在安静集群上丢掉 0.5%–1.5% 的有效通信重叠增量（叠加起来很可观），在嘈杂主机上又放行随机抖动。
3. **LLM 定量先验失准**。前沿 LLM 能定性说清机制，但**零样本加速预测与真实硬件执行负相关**（Spearman r ∈ [−0.49, −0.06]），还会误杀高收益开关：Gemma-4-26B-A4B MoE 上 LLM 预测图编译只有 +2.0%，实测 +55%；双机 Qwen3.5-35B-A3B MoE 上预测加 NCCL 通道会变慢，实测 +10.2%。
4. **单 incumbent 贪心搜索在显存/编译悬崖前失明**。提升吞吐的设置经常单独触发 OOM，必须同时配上省显存的搭档和兼容的 kernel 补丁。Gemma-4-26B-A4B MoE 上关掉激活重算会差 18 GiB 显存、默认 fused kernel 开编译直接挂死——贪心调参器要么反复撞同一个 OOM，要么在局部最优里打转（Auto-Research 在这个负载上卡在 1.29× 出不去）。

一句话总结动机：**训练优化需要"配置旋钮 + 代码补丁"的组合搜索，而 LLM 的直觉不可靠、集群噪声不可忽略、失败代价昂贵——所以需要一个有契约、有验证、有记忆的 Harness，而不是又一个"让模型随便改代码"的 Agent。**

## 三、核心方法与创新点

### 3.1 五阶段工作流：init → doctor → run → report → apply

InfraRSI 把 LLM 假设生成与测量、验证、搜索、经验存储**解耦**，用一个声明式 `infrarsi.yaml` 加轻量适配层（每个训练栈 <15 行 hook）统一 Megatron-Core、FSDP2/TorchTitan、DeepSpeed、HF Trainer/TRL、原生 PyTorch DDP 五大训练栈：

- **init**：解析目标仓库 AST，声明可编辑文件 `editable_files`，对不可动的 `frozen_files`（数据加载、评测脚本、loss 定义、计时器）锁定 SHA-256 摘要——从源头堵死"改计时器造假"。
- **doctor**：跑参考基线、裁剪 warmup、校准集群配对步时噪声、剖析前向/反向/优化器/数据加载/通信各相位、探测互联带宽、评估经验库覆盖度。
- **run**：执行预算化的组合搜索（§3.3），保存每次尝试的原始回执与完整 GPU/API 成本；搜索结束后对最快候选做**背靠背独立复测**，把验证过的观察写回经验库。
- **report**：渲染结构化报告、不变量裁定与资源核算，审计候选源路径。
- **apply**：检查工作区冲突，把晋级的配置与源码 diff 提交（可开新分支）。

### 3.2 固定任务契约与 16 项不变量验证

每个候选 = 一组启动配置旋钮（CLI flag、环境变量、配置键）+ 一组 AST 验证过的源码补丁（如编译 block-sparse/chunked attention、融合 RMSNorm/RoPE/AdamW、桶化梯度范数通信）。优化目标是在**固定任务契约**下最大化对数加速：

$$\max_{a \in \mathcal{A}} y(a) = \ln \frac{T_0}{T(a)} \quad \text{s.t.} \quad \mathcal{I}_k(a) = \mathrm{True}, \; \forall k \in \{1, \dots, 16\}$$

契约锁定模型架构、数据集、有效工作量（每次 optimizer update 的 token 数）、允许的数值精度菜单、优化器协议；16 项确定性不变量覆盖五个验证层：任务层（执行完成、显存上限、token 数、步数、学习率调度、数据顺序、frozen 文件摘要、模型摘要 HMAC）、数值层（loss/梯度容差、无 NaN）、计时层（warmup 裁剪、稳态窗口、防时钟偏移）等。此外每个候选都用**加密签名回执**记录，失败与被审计剔除的尝试也全额计入 GPU 时与 token 成本，杜绝幸存者偏差。

验证区分两个问题：**短视界 loss 一致性**检查数值忠实性（候选没偷偷换精度），**背靠背复测**确认加速可复现（超出配对噪声 $\exp(2\sigma_{\mathrm{pair}})-1$ 的相对裕度）。

### 3.3 预算化组合搜索：三个机制

这是论文技术含量最高的部分，围绕"多起点 + 全局双模型"组织：

**(1) 多起点初始化 + 全局时间/删失显存模型。** 搜索空间被 OOM 边界和编译不兼容分割成不连通的盆地，从单一默认配置出发浪费预算、信任单个模型提案又容易开局崩。InfraRSI 前三次完整试验分别：从经验库中最相似硬件/模型环境的验证配置热启动、从 LLM 先验评分最高的差异化配置出发、随机合法配置锚定全局方差（Qwen3.5-9B 上经验库热启动 Trial 1 就到 1.55×）。随后维护两个全局模型：

- **时间代理模型**：Cholesky 贝叶斯线性模型，对"非参考旋钮设置 + 已验证补丁 + 启用对"的指示特征拟合对数加速，闭式更新后验精度矩阵；
- **显存账本**：**右删失 Tobit 模型**拟合每卡峰值显存 $\hat{m}(a)$，三种执行状态统一处理——正常完成用高斯残差；OOM 失败用删失似然强制 $\hat{m}(a) \ge m_{\mathrm{oom}}$（失败分配的缺口就是所需显存下界！）；近容量 allocator 抖动用区间删失似然限制在 $[0.9 C_{\mathrm{card}}, C_{\mathrm{card}}]$。阻尼牛顿 + 拉普拉斯协方差拟合后，得到标定过的显存可行概率和每个设置的 GiB 价格，**把失败的 OOM 也变成有用的训练数据**——这是全文最漂亮的细节之一。

**(2) 先验校准、失败归因、补全配对（bundle completion）。** 对 LLM 先验做经验贝叶斯收缩（旋钮先验按先验离散度正则化、代码补丁收益乘保守收缩系数 $\kappa_0$），并且**逆向探测**：高影响旋钮被先验打低分或否决、但两倍标准差上行空间超过阈值时，主动试它。失败归因精确到最小冲突元组（只禁"同时出现才炸"的最小旋钮对/三元组），OOM 的设置标记为"需要覆盖缺口的省显存搭档"而不是直接拉黑。于是 Gemma-4-26B-A4B MoE 上：关激活重算（缺口 +18 GiB）配对关 Liger fused cross-entropy（省 14 GiB）再叠 `torch.compile`，凑出 2.75×。

**(3) 高影响旋钮逃逸 + 补丁堆叠。** 把单旋钮效应超过 $\max(0.02, 2\sigma_{\mathrm{pair}})$（约 2%）的划入 Big-Knob 集合，结构化探索（多样化初始、逆向探测、信任域逃逸、禁忌去重、热重启）只在 Big-Knob 上做；连续两次无改善就把信任域从 1 个旋钮扩到 3 个，强制多旋钮跃迁跳坑。验证过的源码补丁在稳定配置上**堆叠**而非互斥地二选一。

### 3.4 两级递归自改进：经验库与跨硬件迁移

run 阶段的验证结果结构化为三类实体写入**跨硬件经验库**：Environment（硬件 roofline、拓扑、软件版本、并行布局）、Observation（完整配置、步时、峰值显存、16 不变量裁定、OOM 缺口与最小冲突元组）、Effect（配对对数加速、噪声底、机制类别）。检索时按机制归一化做跨硬件匹配。

经验不能盲目照搬：同一优化在 H20 和 H200 上**收益符号会翻转**（如 tp=2 在 H20 上 +24%，H100 上 −4%，因为 AllReduce 开销吃掉 GEMM 收益；FP8 注意力在 H200 上反而输 BF16 FlashAttention-3）。InfraRSI 用 roofline 条件化存储机制类别，并在 run 内用实测**在线修订 LLM 先验**、跨集群蒸馏验证过的经验——run 内"先验自纠偏"、run 间"经验再沉淀"，构成两级 RSI 闭环。

## 四、实验结果与分析

四个稠密与 MoE 训练负载、单机双机、H100/H200，与 Auto-Research、METR RE-Bench 脚手架、纯旋钮 OptiCo 在同一任务契约下对比：

| 负载与硬件 | 基线 MFU | OptiCo | Auto-Research | RE-Bench | InfraRSI | 关键发现的组合 |
|---|---|---|---|---|---|---|
| Qwen3.5-9B（8×H100） | 25.3%（1.62 s） | 1.24×（31.5%） | 1.53×（38.6%） | 1.62×（40.9%） | **1.73×（43.8%）** | 显存账本配对（Liger 省显存换关重算 + micro-batch 2）+ 融合归一化 |
| Gemma-4-26B-A4B MoE（8×H200） | 6.4%（3.38 s） | 1.32×（8.4%） | 1.29×（8.3%） | 1.33×（8.5%） | **2.75×（17.6%）** | 补全配对（`torch.compile` + 关 Liger + 关重算）+ 缓存 FlexAttention |
| Qwen3.8-27B（8×H200） | 29.3%（4.50 s） | 1.19×（35.0%） | 1.39×（40.8%） | 1.38×（40.6%） | **1.55×（45.4%）** | 省显存配对 + 融合 RMSNorm/RoPE/SwiGLU kernel + 选择性激活重算 |
| Qwen3.5-35B-A3B MoE（16×H100，2 节点） | 8.7%（1.89 s） | 1.17×（10.3%） | 1.17×（10.2%） | 1.17×（10.3%） | **1.51×（13.2%）** | 逆向探测 32 通道 NCCL + 复合补丁（融合 SwiGLU + 桶化梯度范数） |
| **四负载均值（几何平均 / 平均 MFU）** | 17.4% | 1.23×（21.3%） | 1.34×（24.5%） | 1.37×（25.1%） | **1.83×（30.0%）** | 单机/多机、稠密/MoE 全线领先 |

三个观察：

- **纯旋钮调参很快见顶**（1.23×）：启动 flag 消不掉算子级瓶颈；编码 Agent 则在 OOM/编译冲突前卡住，来不及叠兼容补丁（Auto-Research 在 MoE 上停在 1.29×）。
- **MoE 收益最大**：Gemma-4-26B-A4B 从 6.4% MFU 提到 17.6%，靠的正是"耗显存优化 + 省显存搭档"的组合完成——单看任何一个开关都是死路。
- **逆向探测真的有用**：+55% 的图编译、+10.2% 的 NCCL 通道都是 LLM 先验给差评、靠实测纠偏捞回来的。

**跨硬件经验迁移**（Qwen3.5-9B, 8×H100）：冷启动最终 1.70×、用全部经验包也是 1.70×（>17 trial 都到不了 90% 峰值）；而只用**其他 GPU 型号**的经验做 cross-SKU 迁移，最终 1.82×，第 9 次试验（2.97 GPU·h）就达到 90% 峰值。过滤掉同任务同硬件的"作弊"历史后依然有效，说明经验库学到的是**机制级知识**而非答案记忆。

**离线审计**：1,212 条历史执行回执重新裁定，812 条（67.0%）通过、400 条（33.0%）被拒；40 个系统测试用例（28 个扰动 + 12 个良性）100% 正确分类；密码学回执完整性测试拦截全部伪造。39 条执行（3.2%）只有数值层 L4 能拦住——印证了数值容差验证不可省。

## 五、与 AI 基础设施的关联

这篇论文对 AI Infra 研究者来说信息密度极高：

1. **"Agentic 训练优化"可以工程化，不必玄学**。InfraRSI 证明把 LLM 当假设生成器、把测量/验证/搜索交给确定性 Harness，就能在真实训练仓库上拿到可复现的 1.83×。对 LLM 训练系统、AutoML/AutoTuning 方向（如 DeepSeek 的 kernel 竞赛、各家自动并行工作），这套"契约 + 不变量 + 背靠背复测"是可直接搬用的评估范式。
2. **性能先验必须在线校准**。零样本 LLM 性能预测与实测负相关这个发现，对所有"用 LLM 预测系统性能"的工作（cost model、调度器、编译器 pass 选择）都是当头棒喝：LLM 的定性机制推理可用，定量排序不可信，必须用少量实测做经验贝叶斯纠偏。
3. **删失数据建模值得推广**。OOM 失败不是垃圾数据而是显存需求的下界观测——Tobit 删失回归把失败变成信息。任何带硬约束（内存、deadline、配额）的系统搜索都能借鉴：失败尝试应该进模型，而不是被丢弃或简单拉黑。
4. **噪声校准决定搜索上限**。配对步时噪声 0.04%–6% 的宽谱分布意味着固定阈值调优在两端都失效。对推理服务的 A/B 评测、调度策略的在线实验同理：先量化噪声底，再定接受准则。
5. **跨架构迁移揭示 roofline 敏感性**。tp=2 在 H20 +24%、H100 −4% 这类符号翻转，说明任何"性能经验库"（包括 MLOps 平台沉淀的调优记录）都必须条件化硬件 roofline，否则会把好配置误杀、坏配置照搬。
6. **对推理侧的延伸**。虽然论文聚焦训练，但同样的方法论（组合搜索 + 显存账本 + 经验库）天然适用于 KV cache 管理、并行解码调度、prefill/decode 分离配置——训练与推理的 AutoTuning 正在合流。

## 六、总结与启发

**亮点**：(1) 五阶段契约式工作流把"Agent 改训练代码"这个高危动作关进了 16 项不变量的笼子，奖励作弊在审计里无处遁形；(2) 删失 Tobit 显存模型 + 补全配对，让 OOM 从"搜索终点"变成"信息来源"，直接解锁了 MoE 上 2.75× 的组合优化；(3) 跨硬件经验迁移的对照实验设计得很干净（cross-SKU 过滤），结论可信；(4) 全部失败尝试计入成本、离线审计 1,212 条回执，评测诚实度在同类工作里罕见。

**不足**：(1) 规模有限——只有 4 个负载、最多 16 卡，尚不清楚在百卡以上集群、更长训练周期（数周）上的搜索预算与收益比；(2) 2.75× 的案例依赖特定的 Liger/FlexAttention 交互，换模型家族后组合空间如何变化未充分讨论；(3) 经验库的机制归一化（Environment/Observation/Effect）还是手工 schema，跨厂商硬件（如非 NVIDIA）的泛化是未知数；(4) LLM 后端虽然支持 7 种，但未给出不同提案模型质量对最终加速的消融。

**对后续研究的启发**：递归自改进的正确打开方式可能不是"让模型改自己的代码"，而是"让模型在可验证的契约下改基础设施，把验证过的经验沉淀成可迁移的机制知识"。下一步值得做的包括：把经验库升级为可检索的性能知识库（与性能模型/模拟器联立）、将契约验证扩展到 RL 后训练系统（奖励计算、rollout 调度同样充满作弊空间）、以及把这套框架搬到推理服务的在线调优上。当训练吞吐成为扩展律的硬约束，"会自我优化的训练基础设施"本身就是一种生产力。
