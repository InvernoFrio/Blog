## 二、研究背景与动机

GPU 是 LLM 服务的主导成本，但延迟敏感的推理几乎不可能把 GPU 时刻用满：SLO 约束下总有一些算力闲置。以往的共置（colocation）思路是把 best-effort 的工作（典型如 LoRA 微调）和推理放在一起跑，回收这部分闲置算力。

而 MoE 架构的流行带来了一种全新的闲置来源。MoE 把稠密 FFN 换成一堆专家（expert），router 把每个 token 只送到 top-k 个专家。由于单卡放不下全部专家，主流部署采用**专家并行（EP）**：不同专家放在不同 GPU 上，token 被 dispatch 到对应 GPU、算完再 gather 回来。问题在于路由是输入相关的——**各卡分到的 token 数天然不均**，轻载卡算完自己的专家后只能干等最重的那张卡，这段等待时间就是**气泡（bubble）**。

更关键的是，气泡是"打不死的小强"：学界业界已经用负载均衡路由目标、专家复制与放置、token 重分布、专用通信 kernel 等手段反复优化过路由不均，但论文实测**即便全部用上，气泡仍占 prefill 时间的 8–13%**。既然消灭不掉，能不能用起来？

现有共置系统在这里却失灵了。LLMStation 等系统有三个结构性局限：

1. **调度粒度太粗**——它们在"一次前向/一个训练 step"级别做一次全局调度决策，而气泡发生在**单个 MoE 层内部**，且每张卡的气泡长短不一，需要 per-GPU、per-layer 的细粒度规划；
2. **抓错了阶段**——它们主要利用 decode 阶段和完全空闲的时间，而 EP 气泡主要出现在 prefill；
3. **代价太重**——要么在显存里再放一份模型权重副本做训练，要么把每个模型架构移植到专门的训练引擎里，支持新架构就要手写反向 kernel。

## 三、核心方法与创新点

BubbleTea 的系统名字取得很形象：把气泡当茶杯，往里倒微调这杯"茶"。它由三个关键部分组成。

### 3.1 气泡预测：用 router 的决策提前算出每卡空窗

**核心洞察：气泡长度是可预测的。** 在推理中，router 决定每个 GPU 收到多少 token 是发生在专家计算**之前**的。拿到 token 计数后，BubbleTea 就能估算每张卡的本地专家计算量，进而预测该卡的气泡何时开始、持续多久。论文报告预测的中位误差仅 **8.9 µs**，约为气泡中位长度的 **7%**——这个精度足以支撑调度决策。

这让调度器能在**每个 MoE 层、每张 GPU 上**独立判断"现在有 200µs 空窗，塞一个训练小块"，而不是像现有系统那样全局一刀切。

### 3.2 编译器：从被服务的模型"长出"训练代码

推理引擎只有前向传播；微调还需要反向传播来算 LoRA 梯度。BubbleTea 的编译器做三件事：

1. **读入服务引擎的前向 pass**（包括其推理专用的 MoE kernel 和专家放置布局）；
2. **自动派生匹配的反向 pass**，即训练 step 的计算图；
3. **把训练 step 切成足够短的 chunk**，短到能塞进单个气泡窗口。

由此带来两个直接的好处：

- **权重零复制**：生成的训练代码直接操作推理侧已经加载的权重，不需要第二份权重副本占显存；
- **架构零移植**：支持新模型不需要手写反向 kernel，服务引擎的 MoE 算子和专家布局可以"as-is"复用。

这与 LLMStation（需要第二份权重）和 Mélange/Orion 类系统（需要把架构移植进专用训练引擎）形成鲜明对比。

### 3.3 调度器：气泡内插训练块，气泡外抢 decode 时间

调度策略可以概括为"分而治之"：

- **气泡窗口内**：只在预测出的空窗里执行短训练 chunk，绝不挤占专家计算，保证 prefill 不变慢；
- **decode / 空闲时段**：细粒度的训练运行时本身也更善于利用 LLMStation 原本就抓的 decode 空闲时间；
- **高负载时段**：气泡的价值最大——此时 decode 和空闲时间都被占满，气泡成为唯一的训练算力来源，论文测得气泡贡献的吞吐提升最高达 **27%**。

## 四、实验结果与分析

**实验设置**：4 张 A100 GPU，三个 MoE 模型（含 Qwen3-30B-A3B），两条生产 trace（含 Azure 突发流量 trace），基线为移植了 MoE 支持的 LLMStation 和无协调的 stock trainer（CUDA MPS 共置）。

| 指标 | BubbleTea | LLMStation | 无协调共置（CUDA MPS） |
|------|-----------|------------|------------------------|
| 微调吞吐（对比 LLMStation，三模型平均） | **1.9–6.2×** | 1×（基线） | — |
| 微调吞吐（Azure 生产 trace） | **3.3×** | 1× | 约 1/14 |
| p90 TTFT 偏离（生产 trace） | **+3% 以内** | — | +18% |
| p90 TTFT/TPOT 偏离 ≤10% 的 workload 数 | **50 / 63** | 44 / 63 | — |
| 高负载时气泡带来的额外吞吐 | **最高 +27%** | 无此来源 | 无此来源 |
| p90 TTFT 偏离（全量 workload 最优情况） | 50 个 workload 在 10% 内，生产 trace 在 **7%** 内 | 44 个 | — |

几个值得注意的细节：

1. **气泡是增量而非替代**。BubbleTea 比 LLMStation 多赚的吞吐一部分来自气泡本身，另一部分来自它细粒度的训练运行时对 decode/空闲时间的更充分利用——这是个"副产品式"的系统设计红利。
2. **尾延迟保护很强**。在 63 个 workload 中有 50 个把 p90 TTFT 和 TPOT 都压在单独服务的 10% 以内（LLMStation 只有 44 个），突发流量全程 p90 TTFT 偏离在 3%（图 1）到 7%（摘要）之间，说明气泡内调度几乎不碰推理的关键路径。
3. **突发负载下优势放大**。生产 trace 上 3.3× 的领先幅度和 14× 对无协调共置的碾压，说明调度精度在负载波动时最值钱——无协调共置此时把 p90 TTFT 拉高了 18%，等于用 SLO 换吞吐。

## 五、与 AI 基础设施的关联

这篇论文对 AI Infra 研究的启发相当直接：

1. **推理服务与训练系统的边界在溶解**。共置不再是"推理 + 一个后台训练进程"，而是把训练 chunk 化、编译进推理引擎的执行节奏里。未来的服务引擎可能天生就带一个"碎片算力回收层"，训练、蒸馏、KV 预算建模等 best-effort 工作都从这里排队。
2. **MoE 的负载不均从"要消灭的病"变成"可利用的资源"**。路由均衡依然要做（气泡仍有 8–13%），但系统设计应该假设"均衡之后仍有残余气泡"，并为它设计专用的填充机制。同样的思路可以推广到 pipeline 并行的 stage 间气泡、TP 的 all-reduce 等待等一切"结构性空闲"。
3. **per-GPU、per-layer 粒度的调度成为新基准**。一次前向一个决策的粗粒度调度在异构负载（MoE、混合注意力、多模态）面前越来越不够用。气泡预测依赖 router 的 token 分配这类"运行前可知"的信号，提示我们：**调度器应该更多利用模型内部的先验信息**，而不是只看请求队列。
4. **编译器驱动的训练代码生成降低了共置的工程成本**。"从 forward 自动派生 backward 并切 chunk"这一招，对任何想在推理引擎上叠加训练/适配能力的系统（比如在线学习、个性化 LoRA、推理时自蒸馏）都有复用价值。
5. **对资源调度/成本模型的启发**。8–13% 的 prefill 算力在大规模集群上是真金白银。把气泡回收纳入 GPU 小时的成本核算，可能改变"推理集群 vs 训练集群"的静态划分逻辑。

## 六、总结与启发

**亮点**：

- 问题发现敏锐：在"负载均衡已经很卷"的领域里找到了残余的、结构性的、可预测的闲置资源；
- 系统设计完整：气泡预测 + 编译器自动切 chunk + 权重复用，三件事互相咬合，工程含金量高；
- 评估扎实：不仅比吞吐，还把收益拆到"气泡来源 vs decode 来源"，并用 63 个 workload 的 SLO 达标数说话。

**不足**：

- 实验只覆盖 4 张 A100 的单机规模，EP 气泡在多机 NVLink/RDMA 拓扑下的表现（跨机 gather 的依赖更长，气泡可能更大但更难预测）还有待验证；
- 微调任务是 LoRA 这类 PEFT，全参微调或更大 batch 的梯度累积能否同样塞进 µs 级气泡，存疑；
- 气泡预测依赖 router 决策的可得性，对使用动态 speculative decoding 或非标准路由的服务引擎，适配成本未讨论。

**对后续研究的启发**：把"消灭不掉的系统损耗"当作可调度资源，是这篇论文最有普适性的思维方式。下一个候选对象也许是 EP 之外的通信等待、MoE 的 drop token、甚至 KV cache 换入换出的碎片带宽。谁能预测它们、切碎工作填进去，谁就能在同样的硬件上白捡两位数百分比的利用率。
