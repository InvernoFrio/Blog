# 2026-11-27 模型自主管理上下文：让 Agent 自己决定何时压缩记忆

## 二、研究背景与动机：谁该管理上下文？

今天几乎所有的 agent harness（编码智能体、研究智能体背后的运行时框架）都替模型管理上下文：历史记录（工具调用、工具输出、模型轮次）持续增长，当窗口用量越过阈值（比如 80%），harness 自动触发一次 **compaction**——把早期历史摘要成一段总结塞回去。这种「harness 驱动」的策略简单可靠，但有两个根本问题：

1. **决策权错位**。什么时候压缩、压掉哪些内容、哪些信息必须保留，只有正在执行任务的模型自己最清楚。harness 的启发式规则只能"一刀切"，容易丢掉关键证据——比如一个很久之前读到、但对最终答案至关重要的文档片段。Chroma Research 2025 年提出的 *context rot* 现象也表明，历史越长、噪音越多，模型对相关信息的利用能力越差。
2. **摘要本身是有损的**。harness 让模型生成的摘要是单次单向的降维，被压掉的原始事件通常无法找回。

本文研究的替代方案是 **模型驱动（model-driven）的上下文管理**：把压缩的时机和内容决策直接交给模型。作者在 NVIDIA 开源的 agent harness **NOOA** 中给模型开放了 context API——模型可以：

- **`collapse`**：检查自己的历史，把一段连续的事件替换为一段自己写的摘要（被压掉的事件归档并打标签）；
- **按标签取回**：需要时可以按原始 tag 把归档事件检索回来。

这就把"上下文"变成了模型可以主动编辑的工作记忆，而不是只能被动接受的只读缓冲区。但这条路有几个悬而未决的问题：现有模型真的能管好自己的上下文吗？会不会把好信息压掉？收益是否值得？以及——**推理引擎能否让这种"上下文编辑"变得便宜**？本文给出了迄今最系统的实证回答。

## 三、核心方法与创新点

### 3.1 两种策略的对照设定

作者在 **OfficeQA Pro v2**（90 道关于美国联邦收支的文档问答题，需要在大型文档语料中检索阅读，上下文很快被填满）和 **MLE-bench Lite**（22 个 Kaggle 竞赛任务，需要反复跑实验、改代码、看反馈）两个基准上做对照：

| | Harness 驱动（基线） | 模型驱动（本文） |
|---|---|---|
| 触发时机 | 用量达 80% 预算时自动压缩 | 模型自行决定；提示"用量达 85% 后再考虑压缩"，并附实时用量指示器 |
| 压缩内容 | harness 摘要早期历史，保留初始指令 + 最近 10 条事件 | 模型用 `collapse` 自选事件范围写摘要，原文归档可按 tag 取回 |
| 接近上限 | 无特殊机制 | 请求中注入 context-pressure 警告，观察模型应对 |

上下文预算从 **8K 扫到 512K tokens**。预算越小，context pressure（任务所需信息量 / 窗口容量）越大，等价于模拟更长的任务。预算是请求的硬上限：超限时回退策略先删最旧事件重试，连续三次失败则记为答错。评测模型为 GPT-6.1 Sol、Kimi K3、DeepSeek V4 Pro、Claude Opus 5.5。

### 3.2 模型行为的细粒度刻画

除了任务分数，论文还刻画了模型使用 API 的方式——这是本文最有洞察的部分：

- **调用频率**：GPT、Kimi、DeepSeek 在 42–53% 的任务中至少调用一次压缩；**Opus 只有 4%**。
- **压缩力度**（每次 compaction 后请求缩小的倍数，中位数）：GPT 3.7×、Kimi 2.1×、DeepSeek 1.8×、Opus 1.5×。
- **回溯率**（压完之后又把归档内容取回来的比例）：GPT 19%、Kimi 7%、DeepSeek 3%——压得狠但敢取回，说明 GPT 对"压什么、何时找回"有更完整的策略闭环。
- **高压下的反应**（64K 预算，从第一次压力警告到任务结束）：Opus 多数时候直接收尾交答案；GPT 在 69% 的回合里**先读 API 文档再压缩**，DeepSeek 46% 先翻事件历史，Kimi 则 49% 直接压。

### 3.3 Context Anxiety（上下文焦虑）

即便给了 API，模型也可能过度压缩——明明还有空间就把历史删小。论文借鉴 Igbinedion et al. 2026 的术语称之为 **context anxiety**，并用"首次压缩时已用预算的占比"来度量。结果显示：给了"85% 之后再考虑压缩"的指令时，多数模型能等到接近该点才动手；**去掉这条指令后，部分模型的压缩时机显著漂移**——也就是说，压缩时机对 prompt 措辞高度敏感。这对工程实践是个警钟：模型的上下文管理行为不是稳定的内化能力，而是容易被 prompt 撬动的表面行为。

### 3.4 推理引擎侧的关键创新：编辑后 KV cache 复用

模型驱动管理有一个隐性代价：每次 `collapse` 都改变了后续请求的输入序列，按朴素做法整个上下文要重新 prefill。作者指出，**编辑后的请求中"未变化的后缀"对应的 KV cache 可以直接复用**——只有被编辑的前缀部分需要重算。据此他们实现了 KV cache 编辑支持，**单请求 prefill 计算最多节省 15%，且精度无可测损失**。

这个点的价值超出 15% 本身：它证明「模型编辑上下文」和「推理引擎增量维护 KV cache」是一对可以耦合的接口。如果上下文编辑成为模型的一等能力，Serving 系统必须原生支持 KV 块的删除、替换与部分重算，而不是把每次编辑都当作全新序列。

## 四、实验结果与分析

### 4.1 主结果

| 指标 | 数字 | 说明 |
|------|------|------|
| OfficeQA Pro v2 @ 32K（GPT-6.1） | **21% → 56%**（≈3×） | 模型驱动 vs harness 驱动 |
| Kimi K3 | 最多 **省 41% 输入 token** | 同预算下精度还更高 |
| KV 复用 prefill 节省 | **最多 15%/请求** | 精度无可测变化 |
| OfficeQA Pro v2 @ 32K（整体趋势） | 收益集中在紧预算，512K 时两种策略收敛 | 窗口足够大时管理策略无关紧要 |
| MLE-bench Lite | 收益小得多，仅限最紧预算 | 任务本身需要的上下文较少 |

### 4.2 模型行为对比

| 行为 | GPT-6.1 | Kimi K3 | DeepSeek V4 Pro | Opus 5.5 |
|------|---------|---------|-----------------|----------|
| 使用 API 的任务占比 | 42–53% | 42–53% | 42–53% | **4%** |
| 每次压缩的请求缩小倍数（中位） | **3.7×** | 2.1× | 1.8× | 1.5× |
| 压缩后又取回归档内容 | **19%** | 7% | 3% | 14%（样本少，噪声大） |
| 64K 高压下典型行为 | 69% 先读文档再压 | 49% 直接压 | 46% 先查历史 | 多数直接交答案 |

### 4.3 解读

- **收益的本质是"有选择地保真"**。紧预算下 harness 的一刀切摘要会丢证据，而模型知道哪条事件值得留、哪条可以压，GPT 用 3.7× 的激进压缩 + 19% 的精准回溯把有限窗口用在刀刃上。
- **能力差异大于策略差异**。同样的 API 和指令，Opus 几乎不用——作者推测这与各家训练配方有关：在自动压缩的 harness 里训练的模型不一定学过"何时该压缩、压什么"。GPT 的领先可能来自其开发过程中对类似能力的专门投入（Codex 的 new_context 工具即一例），但论文谨慎地指出：无法确认被测模型的训练细节，也无法确认这种训练能迁移到 NOOA 的接口上。
- **prompt 敏感性是双刃剑**。一句"85% 之后再考虑压缩"就能显著改变行为，意味着该能力既容易用 prompt 激活，也容易因 prompt 措辞不当而退化。

## 五、与 AI 基础设施的关联

这篇论文表面上是 agent 行为研究，实则对 AI Infra 有三层启发：

1. **推理引擎：KV cache 编辑应该成为一等 API**。当前主流 Serving 系统（vLLM、SGLang 等）的前缀缓存以"追加式序列"为假设；一旦模型可以删除/替换历史段，就需要支持 KV 块级的失效、重排与部分 prefill 复用。本文证明这能带来实打实的 prefill 节省（最多 15%），而在多轮 agent 场景（每轮都可能编辑上下文）累积效应会更可观。可以预见，"支持上下文编辑的 KV 管理"会成为 agent 时代推理引擎的标配能力，与 radix tree、paged attention 同等重要。
2. **Agent 服务的成本结构**。紧预算下模型驱动管理以更少输入 token 达到更高精度（Kimi 省 41% 输入 token），意味着上下文管理本身就是一种**免训练的推理成本优化**。对部署长时程 agent 的平台来说，把压缩决策从 harness 移交模型，可能比调 prompt 或换更大窗口更划算。
3. **训练与评估的基础设施缺口**。模型行为的巨大差异（4% vs 53% 的调用率）说明"上下文管理能力"目前几乎不可控。这给 MLOps/训练侧留下明确课题：如何构造训练信号让模型学会何时压缩、如何评估上下文管理策略的优劣（本文的 context pressure 扫描 + 行为指标就是一套可复用的评估框架）。

## 六、总结与启发

**亮点**：

- 把"上下文归谁管"这个长期含糊的问题变成了可量化的对照实验，预算扫描 8K–512K 设计干净；
- 行为学层面的刻画（调用率、压缩力度、回溯率、高压反应）比单一分数更有信息量，尤其是 context anxiety 的 prompt 敏感性发现；
- 没有停留在 agent 层，认真做了推理引擎侧的 KV cache 复用，给出 15% 的实打实节省，闭环了"模型-引擎协同设计"的论点。

**不足**：

- 结论主要由 GPT-6.1 一家撑起，DeepSeek 收益有限、Opus 基本不参与，"模型驱动普遍更好"尚不能成立；
- KV 复用的节省幅度（15%）在单请求层面不大，多轮/大规模 agent 部署下的累积收益没有量化；
- 训练侧只是猜测（"GPT 可能为此训练过"），如何系统性地教会模型管理上下文仍是开放问题。

**对后续研究的启发**：最值得跟进的方向是把上下文管理做成**可训练的能力**——用类似本文的行为指标（压缩时机、力度、回溯准确率）构造 reward 或监督信号，再配合推理引擎的 KV 编辑接口做联合优化。另一个方向是把"上下文压力"显式建模进 serving 调度：当系统知道某个请求处于高压状态时，可以优先调度、预取归档存储，把 agent 的记忆层级（活跃上下文 / 归档 / 外部检索）和存储层级（HBM / CPU / SSD）对应起来——这正是 AI4AIInfra 语境下"记忆即存储层级"的自然延伸。

一句话总结：**上下文管理正在从 harness 的启发式规则，变成模型的一等能力 + 推理引擎的一等接口。谁先把这条链路打通，谁就掌握了长时程 agent 的成本与性能命门。**
