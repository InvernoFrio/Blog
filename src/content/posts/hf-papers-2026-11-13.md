## 二、研究背景与动机

智能体（agentic）负载已经是 LLM 推理需求的主要来源之一：编码（Claude Code）、数学研究（PutnamBench）、计算机操作（OSWorld）等任务都以"请求—工具调用—更新上下文—再请求"的多步循环执行。这类负载对推理系统提出两个传统聊天场景不显著的挑战：

**1. Prefill/Decode 需求多样且随时间漂移。** 不同任务、harness、模型的未缓存输入量和输出量差异极大：OSWorld 每步往上下文追加截图，是 prefill-heavy 负载；Putnam 每次请求生成长推理链，是 decode-heavy 负载。实测它们的最优 PD 切分（xx 个 prefill 节点 + yy 个 decode 节点）从 2P7D 到 6P3D 不等。而且集群的负载组合本身也在变——一项 1170 万请求的生产研究显示用户触发的任务启动随工作日节奏波动，自动触发的则全天均匀分布；即使挑出全局最优的静态切分，在某些时段相对逐 10 分钟最优切分也要损失最多 24% 吞吐。

**2. 智能体的上下文管理改变 KV 复用模式。** harness 会做上下文压缩（compaction）、fork、派生 sub-agent。论文实测：Claude Code 中一次 359 秒 sub-agent 调用返回后，98% 的 prompt 仍与已有 KV 匹配；而一次 12 秒的 compaction 之后，只有 14% 匹配。也就是说，**访问新近度（recency）根本不能预测 KV 是否还会被复用**——真正决定复用的是"活跃分支的上下文里是否还包含这块 KV"。

现有 PD 分离（prefill-decode disaggregation）服务系统的三件套——planner（规划 PD 切分）、cache-aware router（路由请求）、memory pool（共享 KV 池）——在智能体负载下暴露三个问题：

- **切换代价高**：Dynamo 每次切换节点角色要重启 worker，平均耗时 681 秒且节点全程下线；Arrow 虽然原地切换，但被切换节点的 KV 变得不可达，34 次切换共丢失 55.5% 的可复用 KV。
- **算力需求估计不准**：planner 用队列深度、预测 TTFT 等粗粒度信号，会被 sub-agent 并发产生的短时 prefill 突发干扰，触发无谓的昂贵切换；有些 planner 还按全量输入长度估算 prefill 工作量，忽略 KV 复用，高估 prefill 节点需求。
- **KV 复用误判**：cache-aware 路由把请求集中到少数持有前缀的节点上，抬高 P95 TTFT；LRU 淘汰会丢掉正在等待工具/用户的分支的 KV，却留下 compaction 已替换的历史、已结束 sub-agent 的上下文和 KV 传输留下的重复副本。

根源有两个：**算力分配与 KV 缓存管理是耦合的**（引擎把缓存索引在本地状态里，切换角色就丢失或搁浅 KV），以及**各组件依赖的信号太粗**。

## 三、核心方法与创新点

Evolving Infra 的思路可以概括为：先重构数据面（解耦），再让控制面看懂智能体（自适应）。

### 3.1 数据面：对称引擎 + 共享 KV 池 + 集群级 KV 目录

**对称引擎（symmetric engine）**：扩展 SGLang，让每个节点运行同一个同时支持两阶段的调度循环，KV 传输协议复用 Mooncake 的 RDMA 传输、任意两个节点双向可传。planner 改派节点角色时只需换路由类型，无需重启；节点切换在跑完手头请求后 **0.7 秒**完成（36 卡实测均值 6.2 秒，含等待），比 Dynamo 重启（均值 754 秒）快两个数量级以上，且丢失的 KV 复用仅 0.3%。

**共享主机内存 KV 池**：把所有节点的主机内存（L2）汇成一个池，沿用 HiCache 的 L1（GPU）/L2（主机）两级缓存写穿设计，但共享 KV 直接从对端 L2 经 RDMA 拉取，不经过独立存储层中转，省掉一次拷贝。关键改进是**异步预取**：请求还在队列里排队时就完成"拉取到本节点 L2 → 载入 GPU → 广播到节点内所有 GPU"，prefill 一开始就能用；对比 HiCache 在 prefill 开始时才逐层载入、拖慢首 token。decode 节点只写池不读池（读取会拖慢解码），其生成的 KV 留在本机 L2 供分支下一步使用。

**智能体感知的集群级 KV 目录**：在 Dynamo 式前缀树（记录每个节点 GPU/主机内存里的 KV 放置）之上，为每块 KV 在每个节点上维护一个**活跃分支引用计数**。harness 给每个请求打上分支 ID 并在分支结束时上报；路由器为每个分支维护版本号，上下文被改写（compaction）时递增。计数规则精确跟随智能体上下文管理：连续请求只给新增块 +1；compaction 释放被替换历史的计数；sub-agent/fork 新分支对其复用的块 +1；同相（P2P/D2D）KV 传输把计数搬到目标副本，跨相（P2D/D2P）传输则两边都保留计数（下一步两相都需要）。最终每个活跃分支在每相最多持有一份副本的计数。

### 3.2 控制面：在线迭代时间模型 + 保守的在线规划器

**迭代时间模型**。每个请求用工作量 $w=(t_{uc}, t_c, t_{out}, t_{acc})$ 描述（未缓存 prefill token、缓存前缀 token、输出 token、每次解码迭代平均接受 token 数），其中 $t_c$ 来自 KV 目录能找到的最长缓存前缀，$t_{uc}$ 是剩余输入。基于 roofline 假设：

- Prefill 是计算受限的。第 $i$ 个未缓存 token 在因果注意力下要看 $t_c + i$ 个 token，故一个请求计算 $A = t_{uc}t_c + t_{uc}(t_{uc}+1)/2$ 个 query-key 对。单次 prefill 迭代时间：

$$T^{\mathrm{iter}}_{\mathrm{P},n} = c_{n,0} + c_{n,1}\textstyle\sum t_{uc} + c_{n,2}\textstyle\sum A + c_{n,3}\textstyle\sum t_{rst}$$

  分别对应固定开销、未缓存 token、注意力对数、从主机内存恢复的 token（异步预取隐藏了大部分恢复代价）。

- Decode 是访存受限的，主要读模型权重。MoE 层只读被路由到的专家：$B$ 个并发请求、每请求 $t_{fwd}$ 个 token、每个 token 选 $k/E$ 比例的专家，期望读到的专家权重比例为 $\phi(B)=1-(1-k/E)^{t_{fwd}B}$。单次 decode 迭代时间：

$$T^{\mathrm{iter}}_{\mathrm{D},n}(B) = d_{n,0} + d_{n,1}\,\phi(B) + d_{n,2}\,B$$

  上下文长度项被略去——GLM-5.2/Kimi K2.6 的稀疏注意力使得并发 ≥8 时上下文长度只影响 2–7% 的迭代时间。

系数在线拟合：warmup 期间节点以混部模式跑两种相位，用非负最小二乘拟合系数后冻结，之后只周期性重测随负载组合漂移的均值参数。模型形式本身也有泛化价值：在拟合设置之外，单请求预测误差均值 4.2%、2–8 请求批次 6.3%。

**规划器**。每 $T_{win}=600$ 秒一个规划窗口，按窗口内平均工作量 $\bar w$（刻画负载本身，不像队列深度那样被突发扰动）评估所有候选切分的预测吞吐 $\Theta = \min(\sum \mu_P, \sum \mu_D)$（两阶段取瓶颈）。切换采用统计保守判据：窗口分 $m=10$ 个切片，候选切分的增益均值须超过两倍标准误 $\bar g > 2\sigma_g/\sqrt{m}$ 才切换，有效挡住 sub-agent 突发引发的抖动。实测每轮运行平均只切换 **2.0 次**（Dynamo 3.6 次，且 41–100% 的时间偏离最优切分）。

**KV 淘汰与路由**。淘汰按 $(\mathbb{1}[R_b>0], T_b)$ 升序：先淘汰零计数块（被 compaction 替换的历史、已结束 sub-agent 的上下文、传输重复副本）中 LRU 的，之后才动正计数块。路由则直接选预测 TTFT 最小的 prefill 节点（把该节点运行批次剩余时间 + 队列中各请求服务时间 + 自身服务时间加总），不再在"缓存局部性 vs 负载均衡"之间做二选一——因为异步预取让 KV 搬运足够快。

## 四、实验结果与分析

**设置**：9 节点 × 4 张 GB300（TP4），模型为 GLM-5.2（Putnam、CC）和 Kimi K2.6（OSWorld），NVFP4 权重 + FP8 KV cache + MTP 投机解码；主机内存缓存 4 倍于 GPU 内存的 token 量。负载为 mini-SWE-agent@PutnamBench（decode-heavy）、Anthropic 计算机操作 agent@OSWorld 2.0（prefill-heavy、多模态多智能体）、Trie 回放器重放的真实 Claude Code 轨迹（上下文管理最丰富）。基线是 Dynamo v1.5.1 + SGLang Model Gateway + HiCache LRU（公认最强开源动态 PD 分离系统）以及最优静态切分。

**静止负载（三类工作负载 × 三档并发，共 9 组）：**

| 指标 | Evolving Infra 相对 Dynamo | 说明 |
|------|---------------------------|------|
| 吞吐 | 1.10–2.73× | 最高 2.73 倍 |
| 平均端到端延迟 | 1.15–4.12× 降低 | CC 上 3.80–4.12×，OSWorld 2.34–2.69×，Putnam 1.15–1.23× |
| P95 TTFT | 最高 13.92× 降低 | CC、OSWorld 上 3.25–13.92× |
| KV 复用丢失 | 减少 81–95% | Dynamo 的丢失中 34–46% 来自 LRU 淘汰等待中分支的 KV |
| 相位切换耗时 | 6.2 s vs 754 s | 超过 100 倍差距 |

相对最优静态切分（SGLang）也取得 0.98–1.38× 吞吐，且从 3P6D 到 6P3D 的任意初始切分出发，最终平均延迟差异不超过 1.8%（均收敛到 4P5D）。

**负载组合漂移（Putnam → 混合 → OSWorld 连续三小时）：** Evolving Infra 的 PD 切分实时跟随逐 10 分钟最优切分（OSWorld 段收敛到 8P1D），吞吐为 Dynamo 的 2.14 倍、最优静态切分的 1.28 倍；平均 E2E 延迟分别低 2.15×/1.33×，P95 TTFT 分别低 3.58×/1.88×。Dynamo 在大部分时间里 prefill 节点偏少，印证其信号失准的问题。

**消融**：仅靠"对称引擎 + 共享 KV 池 + 复用感知淘汰/路由"（不做在线切分自适应），在同一 4P5D 切分下就有 1.37 倍于最优静态切分的吞吐；其中仅异步 KV 预取一项就把 prefill 节点空闲率从 23.6% 压到 14.4%（1.12× 吞吐）；复用感知路由/淘汰再把 KV 复用丢失从 2.4% 降到 0.7%、每请求未缓存 prefill token 少 31%。在线切分自适应本身只花 0.3% 吞吐，却省掉了昂贵的离线 profiling——仅三小时 CC 轨迹的离线搜索在 256 卡上就要 **10,752 GPU 小时**。此外，模仿 ThunderAgent "暂停智能体保 KV" 的做法在 GB300 上没有增益（0.95×），因为该平台上 KV 容量不是瓶颈。

规模上，收益在 256 张 GB300 上成立，并在 3,072 GPU 的仿真中保持。

## 五、与 AI 基础设施的关联

这篇论文对 AI Infra 研究的启发相当直接：

1. **"智能体感知"正在成为推理服务的一等公民**。论文的核心洞察是：agent harness 的语义事件（分支创建、compaction、sub-agent 结束、分支 ID）是比访问新近度、队列深度好得多的调度信号。这对 LLM 推理服务的设计范式是个提醒——**服务层应该向上暴露/向 harness 索取语义接口**，而不是在黑盒请求流里猜。实现上只需 harness 传两个标识（分支 ID + 上下文改写版本），代价极低。
2. **解耦是降低调整代价的通用手段**。把"节点角色"与"KV 存储"解耦后，切换从 754 秒降到 0.7 秒，控制面才敢于频繁在线优化。这与训练系统里把并行策略与优化器状态存储解耦、与 vLLM 近期的弹性专家并行（elastic EP）方向异曲同工：让资源再配置的边际成本趋近于零，是资源调度研究的先决工程条件。
3. **带统计门槛的在线规划**。$\bar g > 2\sigma_g/\sqrt{m}$ 这种"增益显著才动作"的切换判据，配以刻画负载本身的均值工作量而非瞬时队列信号，对一切在线资源调度（包括训练集群的弹性伸缩、混合负载的 GPU 分时）都有借鉴意义——**先抑制抖动，再谈最优**。
4. **成本模型要贴着硬件瓶颈走**。roofline 式分解 + MoE 专家激活比例 $\phi(B)$ + 区分缓存/未缓存 token，使迭代时间预测误差 <7%。这种轻量解析模型（而非大黑盒性能模型）在编译优化、算子调度里同样可复用。
5. **多层 KV 基础设施的整合路径**：HiCache 的 L1/L2 层级、Mooncake 的 RDMA 传输、Dynamo 的前缀树索引被组合升级而非推倒重来，展示了生产级 AI Infra 的务实演进路线。

## 六、总结与启发

**亮点**：(1) 第一个把 compute 分配与 KV 管理彻底解耦、并按智能体上下文管理语义做 KV 治理的 serving 框架，问题定义（"recency 不等于 reuse"）本身就值回票价；(2) 实验极其扎实——36 卡到 256 卡实测 + 3,072 卡仿真，3 类真实风格负载 × 3 并发 × 漂移场景 × 消融，主要基线是 NVIDIA 生产级框架 Dynamo；(3) 全部控制面决策在线完成，连性能系数都在线拟合，免去每个负载一次的天价离线 profiling。

**不足**：(1) KV 目录的分支引用计数依赖 harness 合作上报分支 ID 和上下文改写事件，对不透明的第三方 harness（或直接 API 调用）如何降级工作，论文未展开；(2) 论文自己指出在 GB300 上 KV 容量并非瓶颈，因此"复用感知淘汰"的收益主要在高负载/小显存场景显现，对不同硬件档位的普适性有待验证；(3) 模型实验只覆盖 GLM-5.2 与 Kimi K2.6 两个稀疏注意力 MoE 模型，稠密模型或线性注意力下的迭代时间模型形态是否仍成立（附录 B 有理论论证，但缺实测）；(4) 代码暂未开源。

**对后续研究的启发**：智能体时代的推理系统优化，重心正从"单请求内效率"转向"跨请求、跨分支的生命周期管理"。下一步自然的问题包括：KV 池与存储层（L3）的统一淘汰策略、多智能体 DAG 的整体调度（而非单分支计数）、以及把同样的"语义信号 + 解耦 + 统计保守在线规划"套件推广到训练侧的弹性资源管理。对做 LLM 推理服务、资源调度、MLOps 平台的同学，这篇值得精读第 3、5 节。
