## 二、研究背景与动机

### 2.1 Agent 服务的资源形态：CGDC

LLM 应用正从单纯聊天转向复杂智能体：一个 **agent session** 会在"模型推理"和"外部工具执行"（编译器、检索器、Bash 等）之间反复交替。论文把这种部署形态命名为 **CGDC（Clustered-GPUs with Distributed-CPUs）**：GPU 以集群节点形式提供共享推理算力，而工具调用跑在分布式 CPU 上，其 CPU/RAM 由外部执行器管理，不占 GPU 准入预算。

这个形态带来两个关键事实：

1. **工具执行期间，session 对 GPU 的需求是"可中断的"**——工具调用的间隙是重新分配推理容量的天然窗口；
2. **工具延迟成为端到端延迟的重要组成**，甚至超过纯推理时间，调度器若不感知"工具何时返回"，就会浪费稀缺的 GPU 容量。

### 2.2 现有系统的两个问题

现有 serving 系统（llm-d、SGLang、vLLM Production Stack、Dynamo、ThunderAgent 等）普遍遵循 **evaluate-then-decide（先评估、再决策）** 范式，问题出在两头：

- **评估端：忽略"工具返回就绪度"。** 缓存感知系统只看 KV 前缀复用，工作流感知系统只预测未来调用，延迟感知系统只估剩余工作量。工具时序信息此前只被当作 KV 保留时间或 token 占用的代理变量（如 Continuum 预测工具时长定 KV 保留、ThunderAgent 对执行工具的 session 做 token 折扣），且都塞进固定加权打分或人工阈值里。
- **决策端：逐 session 启发式，短视且次优。** llm-d/SGLang 按打分逐个路由，但 session 之间在竞争同一节点容量——把容量给了 A，可能就挡住"价值更高的 B+C 组合"。单会话打分 + 贪心放置天然无法做跨会话的联合权衡。

## 三、核心方法与创新点

TAO 框架沿用 evaluate-then-decide 骨架，但两端都做了系统性升级：**评估端构造"价值三元组"，决策端用动态规划联合选择与放置**，且两者解耦，评估接口可独立演进。

### 3.1 会话中断与重启：统一的优化对象

在工具边界处，调度器可以安全地**中断 session**（释放节点资源，KV 前缀可能被逐出但无需重算）；工具返回后再**重启**（恢复准入）。中断与重启共享同一套 session 评估——中断按价值排序决定，被中断者与新到达请求一起进入**等待池**，等待池里的准入与放置即联合优化的对象。注意：这与抢占活跃推理 session 不同，后者会触发昂贵的重算和 KV thrashing。

### 3.2 价值三元组：字典序而非加权和

对每个 session–节点对，TAO 构造**字典序价值三元组**：

$$\boldsymbol{v}_{i,b} = (k_{i,b},\ r_i,\ t_i)$$

- $k_{i,b}$：**时间衰减的 KV 缓存信用**（第一优先级）
- $r_i$：**工具返回就绪度**（0/1 信号，第二优先级）
- $t_i$：**token 占用**（第三优先级）

决策目标是在容量约束下最大化三元组之和的**字典序**（lexicographic）：

$$x^\star \in \operatorname*{arg\,lexmax}_{x \in \mathcal{X}} \sum_{i,b} x_{i,b}\, \boldsymbol{v}_{i,b}$$

其中可行集 $\mathcal{X}$ 要求：每个 session 至多放一个节点、节点 $b$ 上的准入成本之和不超过剩余容量 $C_b$、只允许合法的 $(i,b)$ 配对。

**为什么用字典序而不是加权和？** 三个信号随时间自然演化、各司其职：缓存信用直接避免重复 prefill 所以优先，但它随时间快速衰减；衰减拉平之后，就绪度把"马上要回来的 session"和"还早的 session"区分开；再平手时 token 占用偏向大上下文（优化器同时考虑其更大的容量成本）。免去了手工调权的脆弱性。

### 3.3 时间感知的缓存信用

基于每个目标节点的观测缓存 token 数（无观测则按 token 量 × 缓存率估计，无证据则记 0），按指数半衰期衰减：

$$k_{i,b}(t) = k^0_{i,b}\, 2^{-\tau_{i,b}/h}, \quad \tau_{i,b} = \max(0,\ t - t^{obs}_{i,b})$$

半衰期取 $h = 10$ 秒。动机来自实测：DeepSeek-V4 Flash 在 2 节点（每节点 4×H100）的 trace 中，缓存 token 保留量的分箱中位数随观测年龄显著下降（1800 秒尺度的指数拟合）。这个折扣让"准入价值"对观测新鲜度敏感；物理 KV 的分配、复用、逐出仍由推理引擎控制，调度器只是估价。

### 3.4 工具返回就绪度：连接 CPU 域与 GPU 域

这是论文最具新意的组件。预测器综合四类信号：**工具接口暴露的进度/返回截止时间**（如 Claude Code 的 Monitor 事件、OpenCode 的 Bash 超时终止报告）、**解析到的 sleep 命令**、**工具级历史时长**、**全局历史**（兜底默认 5 秒），证据优先级从直接时序到历史估计依次降级。对已运行 $e_i(t)$ 时长的调用，历史估计 $\widehat{D}_f$ 给出剩余时间：

$$\widehat{d}_i(t) = \max\{0,\ \widehat{D}_f - e_i(t)\}$$

再映射为**二值就绪信号** $r_i(t)$（预测窗口 $H = 1$ 秒）：

- 工具已观测完成 → $r_i = 1$；
- 已超期未归 → 给临时"探针"机会（$a_i b_i$），避免预测失准导致永远"就绪"；
- 否则 → 若预测完成时间（或暴露的截止时间）$z_i(t) \le t + H$ 且预测时间戳 30 秒内刷新过 → 1，否则 0。

实测中该预测相当准：**10,967 次工具调用的最终时长预测 MAE 仅 0.410 秒，82.9% 的误差在 0.5 秒内**（0.5 秒恰为调度周期的一半）。

### 3.5 动态规划联合选择与放置

把"等待池中选哪些 session、各放哪个节点"建成**多维背包 / 广义分配问题**，用容量状态动态规划精确求解。取容量量子 $\Delta$，离散化 $\bar{w}_i = \lceil w_i/\Delta \rceil$、$\bar{C}_b = \lfloor C_b/\Delta \rfloor$，对第 $j$ 个候选：

$$D_j(\boldsymbol{s}) = \operatorname{lexmax}\Big\{ D_{j-1}(\boldsymbol{s}),\ \max_{b\ \text{eligible}}^{\text{lex}} \big[ D_{j-1}(\boldsymbol{s} - \bar{w}_j \boldsymbol{e}_b) + \boldsymbol{u}_{j,b} \big] \Big\}$$

对冻结的离散化问题，"跳过或放置"穷尽了所有可行选择，归纳可证**精确最优**（舍入可能排除离散化前可行的方案）。

工程上三个关键设计：

- 节点特定的缓存观测在 $O(nm)$ 预处理中折入赋值价值；缓存等价节点可聚合成 $g \le m$ 个聚合容量维度（不动物理 KV 块）；
- 规划器跑在**隔离的异步 worker** 里，应用前对实时状态再校验（snapshot 陈旧性有严格条件损失界证明）；
- 开销极低：四副本扫描中准备 + 求解耗时 **< 运行时的 0.12%**。

## 四、实验结果与分析

### 4.1 设置

- **模型/负载**：DeepSeek-V4 Flash（2 节点 × 4×H100）、Qwen3-32B（4 节点 × 2×H100，高并发）、GLM-4.7（单节点 8×H100 TP8，大模型高并发展示）；工作负载为 SWE-bench Lite / SWE-verified（mini-SWE-agent）与 Terminal-Bench 2.0（Claude Code）。
- **基线**：vLLM Scheduler（Round-Robin / Cache-Aware）、Dynamo（KV 感知）、ThunderAgent（token 计数 + best-fit-decreasing 放置，SOTA）。
- **指标**：任务端到端延迟、TTFT、解码吞吐（TPS）。

### 4.2 主结果（摘要）

- **DeepSeek-V4 Flash / SWE-Lite**：相对各列最强基线，延迟降 **2.4–26.8%**，TTFT 降 **7.4–36.3%**，解码吞吐升 **5.1–29.5%**；Terminal-Bench 上延迟与 TTFT 在三个并发档全部领先。
- **Qwen3-32B / SWE-verified**：TTFT 降 **12.9–29.9%**，吞吐升 **4.0–7.8%**；96/160 workers 延迟分别降 8.3%/9.0%（128 workers 时延迟比 ThunderAgent 高 2.5%，唯一的失分点）。

**GLM-4.7 高并发展示（每 run 300 任务）**，这是全文最能说明问题的表格（延迟/TTFT 单位秒，Decode 单位 tok/s）：

| SWE-Lite | ThunderAgent | 999.6 | 7.01 | 773.3 | 1360.4 | 14.24 | 731.1 | 1747.0 | 23.35 | 668.9 |
| SWE-Lite | **TAO** | **887.7** | **6.78** | **869.6** | **1261.9** | **14.10** | **813.7** | **1476.2** | **20.07** | **805.9** |

（对照组中 Dynamo、vLLM RR/CA 在 160 workers 下延迟高达 4300–8200 秒，差距是数量级前的代际差；完整数字见论文 Table 1–2。）一个直观解释来自运行 trace：TAO 在负载中期**用更少的并发运行请求完成了更早的收尾**——准入更稳、避免了尖峰拥塞。

混合负载兼容性实验（Terminal-Bench + SWE-Lite 混合 + AutomationBench，DeepSeek 双节点）同样以 TAO 总体最优；但在 AutomationBench 128 workers 上 TAO 反而落后（延迟 +7.0%），论文如实报告，提示高并发下策略仍有失配场景。

### 4.3 改进归因与消融

以 DeepSeek 32 workers 平衡工作点做拆解：

| 变体 | Decode (tok/s) | 缓存命中 (%) | TTFT 均值 (s) | 工具结束→首token (s) | 暂停等待 (s) |
|------|------:|------:|------:|------:|------:|
| **TAO 完整版** | **1417.97** | **96.31** | **0.154** | **0.203** | **0.972** |
| 去掉缓存信用 | 1398.35 | 96.24 | 0.157 | 0.209 | 1.028 |
| 去掉就绪度 | 1363.06 | 96.16 | 0.161 | 0.227 | 1.067 |
| 两者都去掉 | 1373.51 | 96.24 | 0.182 | 0.213 | 1.025 |
| 换用 ThunderAgent 暂停排序 | 1355.20 | 96.20 | 0.162 | 0.226 | 1.025 |
| DP 换成 BFD 放置 | 1233.72 | 96.05 | 0.195 | 0.235 | 1.081 |

- **缓存估值**：缓存 token 排序使前缀命中率 +0.19pp、暂停等待 −4.5%；再加衰减后命中率 +0.31pp、吞吐 +1.68%。
- **就绪度**：吞吐 +4.03%，工具结束→首 token 延迟 **−10.88%**，暂停等待从 1.067s 降到 0.972s。
- **联合调度**：在 23 个多候选快照中，DP 在 26.1% 的快照上严格优于启发式，其余持平——联合优化的收益集中在容量竞争激烈的决策点。
- **消融共识**：决策端（DP）贡献最大（换成 BFD 掉到 1233.72），评估端两个信号各贡献约 20–55 tok/s，**估值与决策缺一不可**。

## 五、与 AI 基础设施的关联

这篇论文对 AI Infra 研究的启发相当直接：

1. **Agentic Serving 正在重塑推理调度的问题定义。** 传统 serving 只优化"排队 + 放置"，CGDC 场景要求调度器**跨资源域建模**（GPU 准入 × CPU 工具时序）。"工具返回就绪度"这类此前不存在的信号，会成为 Agent 时代调度器的标配输入——类比操作系统从"进程调度"进化到"感知 I/O 等待的调度"。
2. **KV Cache 是 Agent 服务的"会话状态"，估值需要时间维度。** 缓存信用的 10 秒半衰期设计提示：KV 复用价值不是静态的，调度层的**软估值**（不碰物理逐出）与引擎层的**硬管理**（PagedAttention/RadixAttention/TokenCake）正交且可组合——论文已验证与 TokenCake 的集成。
3. **"评估接口 + 优化器"解耦是可复用的系统架构模式。** 价值三元组是可演进的接口，DP 是通用求解器；换工作流感知、换 SLO 感知，只需改评估端。这为 LLM 服务平台的插件化调度提供了范本。
4. **对容量规划的启示：延迟–吞吐权衡随并发非单调。** 实验显示峰值吞吐在 64–128 workers，最低延迟在小并发——Auto-scaling 和配额策略不能只盯单一指标，"最优工作点"需要调度器与容量规划联动。
5. **确定性优化回来了。** 在 LLM 系统一片"学习型调度器"声中，TAO 用经典背包 DP + 精确性证明 + 0.12% 开销证明：当价值信号设计得好、问题被正确地离散化时，组合优化方法在在线调度里依然有硬实力。运筹背景作者（Yinyu Ye）的加入不是偶然。
6. **工具生态接口标准化趋势。** 论文直接消费 Claude Code Monitor、OpenCode 超时报告等工具运行时信号——未来工具协议（MCP 之类）大概率会把"进度/截止时间上报"纳入标准，Infra 层应提前预留这些信号通路。

## 六、总结与启发

**亮点**：

- 问题定义新且准：CGDC 场景 + "工具就绪度"信号，是 Agent 服务调度文献里少见的扎实问题刻画；
- 方法优雅：字典序三元组避免调参，DP 有精确性证明，异步快照有损失界，工程开销 <0.12%；
- 实验扎实：3 个模型 × 多基准 × 多并发 × 混合负载 + 归因拆解 + 消融，负面结果（AutomationBench 128w）也如实报告；
- 对预测误差鲁棒：工具时长预测 MAE 0.41s、82.9% 误差 <0.5s，且用"探针机会 + 30 秒刷新"兜住失准。

**不足**：

- 联合 DP 只在 26.1% 的多候选快照上严格更优，说明多数时刻启发式已够用，收益集中在高竞争时段——对低负载部署吸引力有限；
- 半衰期 $h=10$s、窗口 $H=1$s 等参数虽有 trace 依据，但跨模型/跨工具生态的敏感性分析只做了工具延迟拉长的情形（附录 G）；
- 工具时长预测依赖历史统计与接口提示，面对全新工具或突变负载会有冷启动问题；
- 未开源调度器实现，复现门槛不低。

**对后续研究的启发**：把"工具时序"当作调度一等信号之后，下一步自然的问题是——(1) 与 SLO/优先级的结合（不同 session 的延迟预算不同）；(2) 多智能体编排场景下"会话间依赖"的联合调度（论文已展示兼容性但未建模依赖）；(3) 就绪度预测的在线学习（而非历史统计）；(4) 与推理引擎的更深度融合——调度层估值与引擎层逐出策略的协同优化。对做 LLM 推理服务平台的同学，这篇值得精读第 3 节和附录 B/I。
