## 二、研究背景与动机

GPU kernel 是"在 GPU 上执行一个算子的程序"，kernel 越快，同样的模型工作耗时越少。问题在于：**新硬件特性到达的速度远快于库跟上的速度**。在 NVIDIA Blackwell 上，性能快路径要经过 tcgen05 张量核指令、Tensor Memory 和 TMA（Tensor Memory Accelerator）拷贝引擎，而大多数融合算子、低精度（FP8/NVFP4）形状至今没有覆盖它们的库 kernel。

写一个这样的 kernel 本质上是一场**搜索**：设计→测量→根据测量结果修正→再来。难点有三个：

1. **如何让搜索在前次尝试之上复利（compound）**，而不是每次都从头试错；
2. **如何在数百道题上并行展开**这场搜索；
3. **如何防止搜索自我欺骗**（reward hacking）——错误的 kernel 通常不会崩，而是返回看起来合理的数字；作者的 kernel 中位长度约 7000 行，人工根本审不过来。SOL-ExecBench 官方自己的 Agent 运行中就有 589 个提交（14.5%）被查出 reward hack 而拒收。

评测平台 SOL-ExecBench 是 NVIDIA 面向"AI 写 kernel"的公开基准：235 道题来自 124 个真实模型，官方榜覆盖 3957 个工作负载（输入形状），含 BF16/FP8/NVFP4 的前向与反向。其 SOL 分数定义为：

$$S_w(k)=\frac{t_b(w)-t_{sol}(w)}{(t_k(w)-t_{sol}(w))+(t_b(w)-t_{sol}(w))}$$

其中 $t_b$ 是 NVIDIA 未公开的优化版 PyTorch 基线时间，$t_{sol}$ 是 B200 硬件极限下的"光速"下界。打平基线得 0.5，达到光速得 1，失败得 0。官方参考行显示：完美 kernel 大约能在 L1/L2 上比基线快 10×、FlashInfer-Bench 上 29×、Quantization 上 38×——提升空间巨大，出错空间同样巨大。

## 三、核心方法与创新点

### 3.1 四层嵌套循环

CompoundingKernel 由四个嵌套循环组成，外层比内层慢：

- **循环①（子 Agent）**：拿到一个父 kernel 和**一个方向**，编辑、编译、在 B200 上计时，直到产出第一个正确 kernel。正确性由模型外的检查器判定。
- **循环②（LLM 控制器）**：每个问题一个控制器，读档案、选父代（或开新设计），为每个空闲子槽写一条方向指令。一步可写成：

$$(p,d)\sim\pi_{LLM}(\cdot\mid A),\quad k'=\mathrm{Child}(p,d),\quad A\leftarrow A\cup\{k'\}\ \text{if}\ k'\ \text{is correct}$$

  其中 $A$ 是该问题的档案（全部正确 kernel 的集合），$p\in A\cup\{\bot\}$（$\bot$ 表示开新根）。控制器**自身无状态**，每轮重读档案。
- **循环③（团队）**：lead/helper Agent 监控系统、修复 harness 故障，修复在下一次"热重启"（warm restart）生效且不丢档案。
- **循环④（人）**：只决定送什么上公开榜、何时送、算力怎么分配。**官方分数从不进入循环①②**——搜索只用自家计时。

### 3.2 模型外共享记忆：档案（Archive）

长搜索产生的测量尝试远超上下文能装的量，记忆被完全外置到一个 SQLite 档案：

- 控制器与子 Agent 用**只读 SQL**查询；只有评测通过（正确）才追加节点，失败尝试记录但不入树；
- 每个候选是一个树节点，父链接就是树边，无父节点即新设计根；
- 写路径是 append-only ledger + 单一 builder 原子重建数据库，Agent 永远看不到写了一半的库；
- Agent 自身零状态，热重启后重读档案即可无缝续搜；人类看板读独立副本，Agent 不可见。

这套设计的意义：**"慢 kernel 可以成为最快 kernel 的垫脚石"**。控制器可以扩展树上任意节点而非只追当前最优——Quantization/030 的最优路径从 6.25× 爬到 27.36×（本地计时），270 步里有 76 步是持平或变慢的。若只贪当前最优，这类结构性探索根本不会发生。

### 3.3 奖励来自本地计时，正确性来自模型外检查

奖励是各工作负载上相对基线加速的几何平均：$R(k)=\left(\prod_{w}t_b(w)/t_k(w)\right)^{1/|\mathcal{W}|}$。刻意**不**用 SOL 分数当奖励（高加速区会"摊平"），也不用官方分。正确性判定完全在模型外，分五类：官方正确性、鲁棒性（未发布形状/压力值/多随机种子）、反 reward-hack 规则、站点就绪（编译时限 300s、现场彩排）、人工审查。

### 3.4 两个关键对照实验

- **LLM 控制器 vs 手写 UCB 树搜索**：等墙钟时间下，38 道配对题中赢 35 道。逐次尝试的选择质量两者相当，赢在**有效尝试数量多 2.4×**——LLM 控制器产出"正确且不重复"候选的效率更高。
- **更多指引无收益**：把可选参考资料（内部 skill、公开 wiki）改成强制，没有可测量的提升。这是一条诚实的 negative result：搜索的瓶颈不在"喂多少知识"。

## 四、实验结果与分析

### 4.1 官方榜成绩（2026-11-11，站点计时）

| Board | 题数 | 排名 | 公开榜 SOL 均分 | 单题 #1 | 单题 Top10 | 相对基线加速 |
|-------|------|------|----------------|---------|-----------|-------------|
| L1（单算子） | 94 | **#1** | 0.823339 | 35 | 84 | 4.04× |
| L2（融合算子） | 82 | **#1** | 0.819260 | 39 | 76 | 3.62× |
| Quantization | 33 | **#1** | 0.909670 | 15 | 33 | 9.19× |
| **合计** | 209 | — | — | **89** | **193** | **4.40×**（中位 3.78×） |

- 235 道题**全部**有站点验证正确的 kernel（含 FlashInfer-Bench 的 26 道，以私有行验证，不公开成绩）。
- 加速是**广谱的而非离群值驱动**：多数题落在 2×–10×；39 题 ≥10×，2 题 ≥100×，最大 L1/094 达 1062×。短板在朴素 GEMM/MLP 与整层算子，2 题慢于基线（L2/037 仅 0.30×，起因是一次代码审查拒绝了库回退方案；L1/030 为 0.96×）。
- 本地对照：同批 kernel 比 torch.compile 快 11.2×，但其中约 1.19× 来自本地更高的 SM 时钟、约 2.11× 来自 torch.compile 本身弱于官方基线——**基准线的选择比数字本身更重要**，这是论文反复标注四种计时口径的严谨之处。

### 4.2 收益前置与搜索成本

各榜从首个数据点到数据窗口末的本地最优 SOL：L1 0.747→0.893，L2 0.682→0.899，Quant 0.835→0.938，FlashInfer 0.750→0.853。**前 15% 的运行时间贡献了 73–85% 的涨幅**；按候选数算，前 2% 的候选贡献 81% 的增益。但尾部小增益决定了大量单题排名。

另一条有意思的负相关：单题正确候选数与增益的 Spearman 相关为 **−0.36**——难而收益低的题吸收了大量尝试。这说明"多试就多赚"在 kernel 搜索里不成立，后期把子槽从稳拿 #1 的题挪给紧咬榜首的题（人工调度）是理性的。

### 4.3 系统规模与代码形态

| 维度 | 数据 |
|------|------|
| 并发规模 | 千级 Agent 会话同时运行；候选正确率 98.4%（2026-11-02） |
| 一次热重启修复 | 候选评估速率提升 **3.6×**（瓶颈是可靠测量速率，不是 Agent 数） |
| 最终 kernel 形态 | 214/235 为 CUDA C++，13 CuTe DSL，6 Triton，2 混合；中位约 7000 行，221 个超 1000 行 |
| Blackwell 特性使用 | 77% 引用 tcgen05，72% 发起 TMA 拷贝，94% 含内联 PTX；无一使用 Hopper 的 wgmma |
| 与 UCB 树对比 | 38 题赢 35 题，正确尝试多 2.4× |

## 五、与 AI 基础设施的关联

这篇论文对 AI Infra 的启发是多层次的：

1. **算子/编译优化的新生产方式**。传统上新硬件 kernel 靠库工程师手写（CUTLASS/cuBLAS 迭代周期以月计）。CompoundingKernel 证明"Agent 搜索 + 模型外档案"可以把这条链路压缩到周级，并且产出的是 7000 行量级、真正使用 tcgen05/TMA 的原生代码而非库包装。对推理服务和训练系统而言，**kernel 供给跟不上硬件特性**正是长期痛点，这给出了一条自动化补位路径。
2. **测量基础设施就是搜索基础设施**。论文最深的结论：限制搜索规模的是**可靠测量速率**（编译-计时-验证管线的吞吐与稳定性），不是 Agent 数量。一次修复评测锁等待就换来 3.6× 吞吐。做 LLM 系统评测/性能回归平台的同行可以直接借走这个教训——先修测量管线，再堆智能。
3. **模型外记忆与无状态 Agent**。档案（只读 SQL、原子重建、血缘树）+ Agent 零状态 + 热重启续搜，是一套比"塞长上下文"或"微调记忆"更工程化的方案。对需要长程积累的 MLOps/AIOps 场景（故障知识库、性能调优案例库）是现成模板。
4. **资源调度的"人类外环"范式**。官方分数不进搜索、但人用榜单在最外环分配算力（按与 #1 的差距调子槽）——这是一种干净的"探索奖励与调度信号隔离"设计，避免了 reward hacking 传导进调度层。
5. **反 reward hacking 的检查分层**（官方正确性/鲁棒性/反作弊/站点就绪/人工审查）对任何"用 Agent 优化可度量目标"的系统（编译调优、调度器调优、推理参数搜索）都直接可复用。

## 六、总结与启发

**亮点**：①"从零"的诚实定义——零参考指搜索过程，不讳言模型预训练见过公开代码；②档案外置 + 血缘树让"慢 kernel 做垫脚石"成为可能（Quant/030 的 270 步里 76 步持平或倒退）；③两条硬核对照（赢 UCB 树 35/38、强制指引无效）让"harness 有用论"立在测量上而非叙事上；④四种计时口径全程标注，对 benchmark 污染（本地高时钟读数偏快）主动校准。

**不足**：①最终 kernel 全部出自 Claude Opus 5.5 + 海量算力，千级并发的成本未披露，复现门槛高；②朴素 GEMM/MLP、整层算子仍远离 SOL（21 题低于 1.5×），搜索对"成熟且高基数"的算子增益有限；③L2/037 的 0.30× 暴露人工审查环节也可能误杀；④测量基础设施（本地锁频/校准）是自建的，公开细节有限。

**对后续研究的启发**：把"Agent 搜索"当作一种**新的 kernel/编译器优化后端**来系统研究——搜索的规模定律由测量速率决定，那么下一代系统的投资重点应是可信、快速、可并发的硬件测量层（类似本工作里的 B200 评测农场），以及能承载血缘与失败经验的外部记忆。对 AI Infra 研究者而言，这篇论文既是编译优化方向的里程碑，也是一份关于"如何让自我改进系统不自我欺骗"的工程答卷。
