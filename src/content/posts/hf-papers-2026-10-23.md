## 一、论文基本信息

- **标题**：Cache Engineering for Agents
- **链接**：[arXiv:2610.28577](https://arxiv.org/abs/2610.28577)（2026-10-20 提交，cs.CL）
- **作者**：Tianyu Fu†、Ruoxi Wang†（共同一作）、Zihan Min、Zhongqi Ren、Zhihao Li、Tengxuan Liu、Shengxu Mu、Hanling Zhang、Yu Wang（通讯，yu-wang@tsinghua.edu.cn）
- **机构**：清华大学（Tsinghua University）+ 香港中文大学（The Chinese University of Hong Kong）
- **代码**：[https://github.com/thu-nics/AKV](https://github.com/thu-nics/AKV)（AKV 服务引擎开源）

## 二、研究背景与动机

LLM 智能体正在处理越来越复杂的长程任务：反复推理、调用工具、观察环境，一条轨迹能积累几百轮交互。这篇论文一上来就给了一个很有冲击力的数字：在他们的实测中，**KV cache 的读取占了 API 总成本的 82.4%**。也就是说，智能体跑长任务时，烧钱的主力不是生成 token，而是反复读取那越滚越大的 KV 缓存。而且轨迹一旦超过模型最大上下文长度，注意力质量还会劣化，精度跟着掉。

现有的主流对策是 **context engineering（上下文工程）**：把历史消息裁剪（trim）或摘要（summarize）。但这条路有一个结构性矛盾——

1. **改文本 = 作废缓存**。历史消息位于轨迹前缀，改写它会让后面所有 KV 状态失效，触发昂贵的 **re-prefill**：改得越早，需要重新预填的保留后缀越长。trim 方法在实测中（只留最近 12 轮工具响应）成本反而涨到全上下文基线的 **1.85 倍**。
2. **为省 re-prefill 只能激进压缩，又伤精度**。常见 harness（如 Pi、OpenAI 的做法）干脆等上下文到阈值再一次性摘要/裁剪，只留几轮最近对话。48K 阈值的摘要方法确实省了约 7% 成本，但**精度掉了 5 个百分点**——中间轮次里有用的信息被一起扔了。

这就是"re-prefill 成本 vs 信息保留"的两难。作者的洞察是：**矛盾的根源在于大家都在文本层动手，而真正决定推理成本与行为的是 KV 缓存本身**。能不能不改文本，直接操控缓存？

## 三、核心方法与创新点

### 3.1 Cache Engineering：三个缓存原语

论文提出 **cache engineering**：智能体直接控制活跃 KV 缓存 $\mathcal{C}$，逻辑 token 序列（文本轨迹）原封不动。在标准的 `append` 之外，新增两个操作：

- **$\operatorname{drop}(P)$**：把选中的 KV 条目从后续注意力中移除，$\mathcal{C} \leftarrow \mathcal{C} \setminus \{C_i : i \in P\}$。保留的状态、位置编码、文本轨迹都不变，也**不需要 re-prefill**。注意 drop 只影响"未来注意力看什么"，不改写历史——保留下来的缓存里仍带着从被 drop 历史中计算出的信息（这也是精度不掉反升的原因之一）。
- **$\operatorname{repos}$**：重新定位保留键的位置编码。若保留 $r$ 个条目，位置索引重置为 $0,\dots,r-1$，下一个 token 从 $r$ 开始。对 RoPE 来说只需旋转键向量：

$$K \leftarrow R(q)R(p)^{-1}K$$

其中 $R(p)$ 是位置 $p$ 的旋转矩阵，value 保持不变。这一步把位置索引从逻辑轨迹长度中**解耦**出来——否则 cache 再小，位置索引也会涨到模型上限。

- 操作序列 $o_{1:m} = (o_1, \dots, o_m)$，$o_j \in \{\operatorname{append}(x), \operatorname{drop}(P), \operatorname{repos}\}$，从空缓存出发唯一确定当前缓存状态。

### 3.2 关键发现：缓存状态是历史依赖的

这是全文最有理论味道的观察。标准 KV cache 中 token 前缀**完全决定**缓存状态，所以 prefix matching 可以放心复用。但引入 drop 后：**同样的 token 序列、同样的保留位置，不同操作历史可以产生不同缓存状态**。论文的例子：三条轨迹都保留 B 和 C，但 C 的 KV 在①中计算时看得见 A 和 B，在②中看不见 A（先 drop 后 append），在③中连 B 的前缀历史都不同——三者的 C 缓存两两不同。于是服务系统必须同时追踪 **token 历史和缓存操作历史**，单纯的前缀匹配会错误复用。

### 3.3 AKV 服务引擎：把操作历史装进 radix tree

为此作者联合设计了 **AKV** 服务引擎（基于 SGLang），三个支柱：

1. **无状态接口**。扩展现有 LLM API：`messages` 字段照旧描述完整逻辑 token 序列，新增可选 `cache` 字段，用 operate-after 语法声明 drop/reposition 操作（按消息下标触发）。客户端无需追踪服务端哪些缓存驻留，服务端内部管理有状态的复用/驱逐/恢复；每个请求的输出分布与物理缓存驻留无关，保证请求隔离。
2. **扩展 radix tree + drop 感知驱逐**。在 drop 触发点插入 **drop node**，prefix matching 同时匹配 token 前缀和操作前缀，正确区分历史依赖的缓存分支。驱逐时：某个 KV 条目只有在没有任何在途计算/恢复需要它时才可释放；被 drop 的缓存优先于已完成请求的缓存被驱逐（后者下一轮更可能复用）。物理存储释放后树节点留空占位，后代仍可被前缀匹配找到。`repos` 同理产生"位置版本"分支：不同请求对同一缓存索要不同位置编码时，复制缓存并旋转 key（copy-on-rotate），原版本留给还在用它的请求，各位置版本独立驱逐。
3. **Segment-batch attention 单趟恢复**。被驱逐的缓存要在一次 prefill 内重建：注意力按 drop 触发点分段，每段对自身 token 因果注意力、并能看到更早段的活跃缓存；被 drop 的缓存对后续段不可见、但对当初使用它的早期段仍可见。只有注意力分段，FFN 仍整序列一批处理——避免每个分段重复读 FFN 权重（显存流量大头）。

### 3.4 策略：rolling drop、RSI、Cache-as-Tool

- **Tool-response rolling drop**（主力策略）：保留全部推理（reasoning）缓存和最近 12 轮工具响应的 KV，更老的工具响应 KV 滚动丢弃。依据是注意力实测：老 token 注意力低，且同等相对位置下工具响应比助手消息注意力低。
- **RSI（递归自改进）**：因为缓存策略变成了可编程的原语序列，策略本身可以被"智能体搜策略、评估、再改进"。用 MiniMax-M2.7 在 20 个 BCP 任务上迭代优化策略，在 100 个留出任务上评估。
- **Cache-as-Tool（CAT）**：把缓存管理暴露为工具，让智能体自己决定何时缩减、保留什么。

## 四、实验结果与分析

### 4.1 设置

三个模型（MiniMax-M2.7、GPT-OSS-120B、MiroThinker-1.7-Mini），四个长程 agent 基准（BrowseComp-Plus、GAIA-Text、SWE-bench Verified、xbench-DeepSearch）。基线两个：**Standard**（模型特定高阈值摘要：GPT-OSS/MiniMax 96K、MiroThinker 192K）和 **Text Engineering**（统一 48K 阈值摘要）。AKV 的 rolling-drop 阈值与 Standard 对齐，成本按 Groq/官方费率计，且**故意按缓存命中价对旋转 token 计费**（保守高估）。服务实验：8×A800-80GB（4 prefill + 4 decode，TP=4，BF16）。

- 各自峰值吞吐下，AKV（并发 14）对 Standard（并发 12）：平均请求延迟约 **1.5x 加速**，P95 延迟约 **1.51x 加速**，输出吞吐约 **1.18x**（输入吞吐按全部逻辑 token 计，差距更大，因为 AKV 复用保留缓存、Standard 要反复 re-prefill）。

### 4.4 消融：drop 什么、何时 repos

表 3：GPT-OSS-120B 各基准前 100 任务的 drop 目标与 repos 消融（分数 / 成本）

| 策略 | repos | BCP | SWE |
|---|---|---|---|
| Standard | ✗ | 56.0 / 13.5 | 41.0 / 19.1 |
| Tool drop | ✗ | 55.0 / 7.1 | 41.0 / 9.4 |
| Reasoning drop | ✓ | 56.5 / 8.2 | 36.5 / 14.2 |
| Both drop | ✓ | 56.5 / 8.7 | 34.5 / 7.8 |
| **Tool drop** | ✓ | **62.0** / 10.9 | 41.0 / **9.5** |

- **只 drop 工具响应缓存 + repos 是最优组合**：BCP 通过率 62% vs 不用 repos 的 55%——repos 让探索能越过原本会终止执行的位置索引上限。
- drop 推理缓存（单独或连同工具响应）在两个基准上都更差——推理链里的信息确实被后续决策用到。

### 4.5 RSI 与 Cache-as-Tool

- **RSI**：第 3、6 轮迭代产出的策略在留出 100 任务上比人工设计的 rolling drop 再省 **15.6% / 17.8%**（相对 Standard），精度持平。缓存策略可以"递归自改进"，这是 cache engineering 可编程接口带来的独特红利。
- **Cache-as-Tool**（100 任务 BCP 子集）：GPT-OSS-120B 分数 61.0（Standard 52.1 / Text Eng. 50.0），成本 12.1 分（Standard 13.4）；MiniMax-M2.7 分数 64.0（Standard 56.0 / Text Eng. 61.0），成本 5.4→5.9（执行了更多轮次）。让智能体主动管理缓存，两个模型上都拿到最高通过率。

## 五、与 AI 基础设施的关联

这篇论文对 AI Infra 研究的启发相当密集：

1. **LLM 推理服务**：AKV 是第一个把缓存控制权从系统层"下放"给上层智能体的服务引擎。传统 serving（vLLM/SGLang 的 prefix caching）假设 token 前缀决定缓存状态；cache engineering 打破了这个假设，**操作历史成为缓存身份的一部分**。drop node、位置版本分支、drop 感知驱逐，本质上是把缓存管理从"按 token 索引"升级为"按操作历史索引"——任何支持 agent 长轨迹的 serving 系统迟早要面对这个问题。
2. **成本结构再认识**：KV 读取占 API 成本 82.4% 这个数字提醒我们，agent 时代的降本重点是**缓存 I/O 与存储**，而不是单看 FLOPs 或生成长度。定价、容量规划、SLA 都该按"活跃缓存足迹 + 缓存读取量"来算。
3. **KV 分层存储与缓存复用**：segment-batch attention 的"单趟恢复"思路（注意力分段、FFN 不分段）对分层 KV（本地 HBM / CPU / 远端存储）的恢复路径设计有直接参考价值——恢复要凑整成一次 prefill，而不是多趟前向。与同期"远程 KV 层反而拖慢 prefill"的实测观察（arXiv:2610.21500）互为印证：缓存复用的收益必须扣除恢复/搬运代价，需要两阶段代价模型判定"命中是否值得"。
4. **资源调度**：高并发下 Standard 的 re-prefill 引发 KV 压力→解槽位减少→延迟爆炸的连锁反应，说明 agent 负载的调度器必须把 **re-prefill 工作量**当作一等公民（PackServe 等 SLO-aware 调度工作也在同一方向）。AKV 让 re-prefill 几乎消失，等于给调度器减负。
5. **编译/内核优化**：segment-batch attention、copy-on-rotate 的 key 旋转（$R(q)R(p)^{-1}$）都是典型的可融合算子，对 kernel 生成器（如 CAKE 一类编译器-智能体协同优化）是很好的目标负载；RoPE 重定位的批量化实现值得单独写 kernel。
6. **AI4Infra / 自改进系统**：RSI 优化缓存策略是"用智能体优化基础设施策略"的一个干净实例：策略空间由缓存原语定义（可编程、可评估、可回放），收益直接量化（成本/精度），比端到端 RL 训练更轻、更可控。这给 AIOps 与策略搜索类工作提供了一个可复制的模板。

## 六、总结与启发

**亮点**：

- **问题重构漂亮**：从"怎么压缩上下文"转到"怎么操控缓存"，一举绕开 re-prefill 两难；drop/repos 的形式化干净，可编程接口直接催生 RSI 和 Cache-as-Tool 两种高级玩法。
- **系统与算法联合设计**：识别出"缓存状态历史依赖"这一新挑战，并用扩展 radix tree、drop 感知驱逐、segment-batch attention 三件套给出完整解法；接口保持无状态、兼容现有 API，工程上可落地。
- **实验扎实**：三模型 × 四基准 + 服务层吞吐/延迟 + 消融 + RSI 留出评估，成本计算还故意高估 key 旋转开销，结论稳健。

**不足**：

- 主力策略（rolling drop）相对简单，"保留最近 12 轮工具响应"是启发式；RSI 与 CAT 的收益在小规模任务集（20 训练 / 100 评估）上验证，规模上去后的策略泛化性未知。
- `repos` 依赖 RoPE 旋转的精确等价，对其他位置编码（如 ALiBi、绝对位置）的适配需要额外设计；repos 引入的"位置版本"会带来额外显存副本。
- drop 之后保留缓存中"残留"的被删历史信息既是优势也是不可控因素——模型行为的可解释性与审计性变弱了。

**对后续研究的启发**：

- 缓存原语可能继续丰富：`merge`（聚合低注意力条目）、`compress`（量化/低秩近似活跃缓存）、按需 `restore`（把 drop 的内容按查询需要召回）都是自然延伸。
- "操作历史作为缓存身份"的思想可以推广到**多智能体共享缓存**与**跨会话持久缓存**：谁改过缓存、何时改的，进入缓存索引。
- 对 agent 框架作者：与其在 harness 里堆摘要逻辑，不如把"缓存预算 + 丢弃策略"做成显式可调的接口层，甚至交给智能体自己管理（CAT 的结果支持这一点）。

一句话总结：**别再跟文本较劲了，去捏缓存**——把 KV cache 从服务系统的内部实现细节，升级为智能体可编程的第一类公民，成本、延迟、精度三者可以同时变好。
