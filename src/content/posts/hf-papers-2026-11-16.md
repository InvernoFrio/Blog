## 一、论文基本信息

- **标题**：Evolving Infra: Agent-Adaptive LLM Serving at Scale
- **链接**：[arXiv:2611.12304](https://arxiv.org/abs/2611.12304)（v2，2026-11-12）
- **代码**：[github.com/mit-han-lab/EvolvingInfra](https://github.com/mit-han-lab/EvolvingInfra)（已开源）
- **机构**：Georgia Tech、UIUC、UC Berkeley、NVIDIA、OpenAI、MIT
- **作者**：Hao Kang、Weili Xu、Ziyang Li（共同一作）、Zheng Du、Hanchen Li、Tian Xia、Song Bian、Tushar Krishna、Huizi Mao、Ion Stoica、Song Han（通讯，MIT Han Lab）

作者阵容相当豪华——Song Han 组的系统工作，加上 Ion Stoica（Ray/vLLM 背后的灵魂人物）和 Tushar Krishna（GPU 体系结构专家），是典型的"推理系统 + 体系结构 + 生产实践"三线联合。基线选的是 NVIDIA 生产级框架 Dynamo，对比目标非常务实。

## 二、研究背景与动机：智能体负载正在"打破"传统推理服务的假设

智能体（Agentic）负载已经是 LLM 推理需求的主要来源：软件工程（Claude Code）、数学研究（PutnamBench）、计算机使用（OSWorld）等场景下，智能体以"步骤"为单位执行任务，每步包含一次模型请求和触发的工具调用。这带来两个关键事实：

1. **相邻请求共享长前缀**，KV cache 跨步骤复用潜力巨大；
2. **Prefill/Decode 需求比例高度动态**，而且传统信号全部失灵。

论文用三个观察把问题钉死：

- **不同智能体的最优 PD 分离比例（xxPyyD）差异巨大**：OSWorld 每步往上下文塞新截图，是 prefill-heavy，最优约 6P3D；Putnam 每次生成长推理链，是 decode-heavy，最优约 2P7D。
- **负载组合随时间漂移**：当集群负载从 Putnam 切向 OSWorld 时，每 10 分钟窗口的最优 split 从 3P6D 移到 7P2D；即使是"最好的静态 split"（5P4D），在两端时段也会损失高达 **24% 吞吐**。
- **访问新近度（recency）不预测 KV 复用**：Claude Code 轨迹中，一次 359 秒的子智能体调用之后，98% 的 prompt 仍命中旧 KV；而一次 12 秒的上下文压缩（compaction）之后，只有 14% 命中——压缩刚"最近访问"过这些历史，但它们已被摘要替换，永远不会再被用到。

现有生产系统（planner + cache-aware router + memory pool 三件套）在智能体负载下暴露三大问题：

| 问题 | 表现 | 实测代价 |
|------|------|----------|
| 相位切换昂贵 | 切换需重启 worker 或搁浅本地 KV | Dynamo 平均每次切换 681s；Arrow 34 次原地切换丢 55.5% 可复用 KV |
| 算力需求误估 | 用队列深度/预测 TTFT 等粗信号；按全输入长度估 prefill | 子智能体突发导致无效切换；忽略 KV 复用高估 prefill 节点需求 |
| KV 复用误判 | cache-aware 路由把请求压到少数节点；LRU 淘汰 | P95 TTFT 被热点节点拖高；等待工具/子智能体的分支 KV 被 LRU 淘掉（占 CC 丢 KV 的 34–46%） |

根源有两个：**算力分配与 KV 管理耦合**（引擎把 KV 索引在本地状态里，节点一切换角色就作废），以及**三大组件都依赖粗粒度信号**，看不透智能体的工作负载和上下文管理。Evolving Infra 要做的就是把这两件事同时解掉。

## 三、核心方法与创新点

整个框架分两层：**基础设施层**（让切换变便宜）+ **决策层**（让决策变聪明）。

### 3.1 基础设施层：解耦算力分配与 KV 管理

- **对称引擎（Symmetric engines）**：每个节点同时支持 Prefill 和 Decode 两种角色，planner 可在运行时改派角色，无需重启 worker、节点也不下线。切换时只需等在跑的请求收尾，节点继续服务。
- **共享主机内存 KV 池**：所有节点的 host memory 组成一个共享 KV 池（L2 层容量为 GPU 显存 L1 的 4 倍），KV 不绑定节点角色——切换后照样可读。取回通过异步 fetch 隐藏延迟，请求还在排队时就开始拉 KV。
- **集群级 KV 目录（KV directory）**：为每个 KV 副本记录"还有多少活跃分支引用它"（引用计数），并响应智能体上下文管理事件（compaction 替换历史、子智能体结束、fork 等）和 KV 传输来更新计数。这是全篇最关键的"新信号"：**它把"哪些 KV 还会被用"从猜测变成事实**。

效果：Evolving Infra 的一次相位切换平均只要 **6.2 秒**（含等待在跑请求），比 Dynamo 重启（754 秒，且节点全程下线）快 100 倍以上，且不丢 KV。

### 3.2 决策层之一：在线迭代时间建模 + 稳健的 PD split 规划

每个请求用工作量四元组刻画：w = (t_uc, t_c, t_out, t_acc)——未缓存 token 数、缓存命中 token 数、输出 token 数、每次迭代推进的 token 数。其中 t_c 直接来自 KV 目录找到的最长缓存前缀，**显式区分缓存命中与未命中**，这是对智能体负载准确建模的关键。

**Prefill 迭代时间模型**（compute-bound 为主，式 1）：

```
T^iter_{P,n} = c_{n,0} + c_{n,1}·Σt_uc + c_{n,2}·ΣA + c_{n,3}·Σt_rst
A = t_uc·t_c + t_uc·(t_uc+1)/2
```

A 是 causal attention 下的 query-key 对数（第 i 个未缓存 token 要回看 t_c 个缓存 token 和前 i 个新 token），t_rst 是从主机内存恢复的 token 数。系数在线拟合，无需离线 profiling；附录证明该式对滑窗/线性/稀疏注意力（含 GLM-5.2 的 DSA）同样成立。

**Decode 迭代时间模型**（memory-bound 为主，式 2）：

```
T^iter_{D,n}(B) = d_{n,0} + d_{n,1}·φ(B) + d_{n,2}·B
φ(B) = 1 − (1 − k/E)^(t_fwd·B)
```

有意思的是 MoE 项：每 token 只激活 k/E 比例的专家，B 个请求、每请求 t_fwd 个 token 合起来命中的专家占比 φ(B) 随 batch 大小变化，因此 decode 时间不是 B 的简单线性函数。由于 GLM-5.2/Kimi K2.6 每 token KV 极少且稀疏注意力只读部分 KV，上下文长度对 decode 迭代时间影响仅 2–7%，模型干脆省略该项。

**在线规划器**：每 600s 规划窗口（分 10 个切片）评估各候选 split 的吞吐 Θ = min(Σμ_P, Σμ_D)（木桶效应：慢的相位定全局），用**窗口内每请求平均工作量 w̄** 而非瞬时队列深度做输入——w̄ 刻画的是负载本身，子智能体突发几乎不动它。切换需"统计显著"：候选 split 的平均增益 ḡ 必须超过 2 倍标准误（ḡ > 2σ/√m）才执行，短突发骗不过这个检验。实测每轮运行平均只切 **2.0 次**，而 Dynamo 切 3.6 次且有 41–100% 的时间偏离最优 split。

### 3.3 决策层之二：KV 复用感知的淘汰与路由

- **淘汰**：按 key (𝟙[R_b > 0], T_b) 升序淘汰——引用计数为 0 的块（被 compaction 替换的历史、已结束子智能体的上下文、传输留下的重复副本）优先按 LRU 出局；有活跃分支引用的块最后才动。对比 LRU："等工具时挂起的分支"KV 被保住了。
- **路由**：既然异步 fetch 让取 KV 变快，就不再为保缓存亲和性把请求压到热点 prefill 节点，而是预测每个节点的 TTFT（式 7：在跑批次剩余时间 + 队列中请求服务时间 + 本请求服务时间），发给预测 TTFT 最小的节点，KV 在排队期间异步拉取。

## 四、实验结果与分析

**设置**：36 张 GB300（9 节点 × 4 卡，TP4），GLM-5.2（Putnam/CC）与 Kimi K2.6（OSWorld/漂移实验），NVFP4 量化 + FP8 KV cache + MTP 投机解码。三个负载：PutnamBench（decode-heavy、无上下文管理）、OSWorld 2.0（prefill-heavy、多模态多智能体）、Claude Code 真实轨迹回放（上下文管理最丰富）。基线：NVIDIA Dynamo v1.5.1 + SGLang PD 分离最优静态 split。扩展实验到 256 卡与 3072 卡仿真。

**平稳负载（9 组并发设置）**：

| 指标 | Evolving Infra vs Dynamo |
|------|--------------------------|
| 吞吐 | 1.10–2.73× |
| 丢失 KV 复用 | 减少 81–95% |
| 平均 E2E 延迟 | 降低 1.15–4.12× |
| P95 TTFT | 最高降 13.92× |
| vs 最优静态 split 吞吐 | 0.98–1.38× |
| 相位切换耗时 | 6.2s vs 754s（>100×） |

分负载看平均 E2E 延迟改善：CC 3.80–4.12×、OSWorld 2.34–2.69×、Putnam 1.15–1.23×。规划器自动选出 CC 用 3P6D–4P5D、OSWorld 用 8P1D、Putnam 只留 1–2 个 prefill 节点换吞吐（P95 TTFT 略升、平均延迟降，是明确的取舍）。注意在 decode-heavy 的 Putnam 上 P95 TTFT 会输给 Dynamo——这是把吞吐最大化的代价，论文没有回避。

**负载漂移实验（Putnam → OSWorld 三段各 1 小时）**：

| 对比对象 | 平均 E2E 延迟 | P95 TTFT | 吞吐 |
|----------|---------------|----------|------|
| vs Dynamo | 降 2.15× | 降 3.58× | 2.14× |
| vs 最优静态 split | 降 1.33× | 降 1.88× | 1.28× |

PD split 曲线紧跟每 10 分钟窗口的 profiled 最优值，OSWorld 时段稳定在 8P1D。

**消融**：

- 对初始 split 不敏感：4 种初始 split（3P6D–6P3D）下平均 E2E 延迟波动 ≤1.8%，全部收敛到 4P5D；
- 基础设施 + KV 感知淘汰/路由（不开在线规划）就拿到最优静态 split 的 1.37× 吞吐；
- 单独异步 KV fetch 就有 1.12×（把 prefill 节点空闲率从 23.6% 压到 14.4%）；
- 相比 cache-aware 路由，丢失 KV 复用从 2.4% 降到 0.7%，每请求未缓存 prefill token 少 31%；
- 最重载 prefill 节点排队时间是平均的 1.75–1.85×（cache-aware 路由下是 2.29–2.61×）。

## 五、与 AI 基础设施的关联

这篇是今年 AI4AIInfra 方向最"系统"的一篇，启发至少有四点：

1. **智能体上下文管理是调度的一等公民**。compaction、fork、子智能体、长暂停这些 harness 行为，直接决定了 KV 的生死。谁还用 LRU + 访问新近度管智能体负载的 KV，谁就在系统性地丢钱。Serving 系统应该向 harness 暴露/订阅生命周期事件，而不是从 token 流里猜。
2. **粗信号时代结束了**。队列深度、输入长度、访问历史都看不透智能体负载；显式区分"缓存命中/未命中 token"的迭代时间模型 + 统计显著性检验的切换策略，是比 RL 调度器更便宜也更稳的路线。对做推理服务或调度器研究的人，这套"在线辨识 + 保守切换"的范式值得直接借鉴。
3. **解耦是普适设计原则**。算力分配与 KV 管理解耦（对称引擎 + 共享池 + 引用计数目录），换来 6 秒级切换和几乎为零的 KV 损失。任何"资源角色"和"状态存放"耦合的系统（不只 PD 分离，也包括训练并行的重切分、显存卸载）都有同样的病。
4. **规模化的信号**：附录 D.2 显示 256 卡以上聚合 split 的重要性下降、节点间不均衡上升，3072 卡仿真下需要层级化调度。这对大规模集群的调度架构（全局规划 + 局部自适应）是个前瞻提示。

不足也顺便说：模型为 dense/主流稀疏注意力推导，KV 每 token 极重的模型（如大 GQA/MQA 前的旧架构）下 decode 项要重新加回来；Putnam 上 P95 TTFT 的取舍说明吞吐最优与延迟 SLO 之间还需要显式的多目标权衡；此外依赖 harness 暴露上下文管理事件，在闭源/不透明 harness 下信号获取是个工程前提。

## 六、总结与启发

**亮点**：三个创新（对称引擎 + 共享 KV 池 + 引用计数目录、在线迭代时间建模 + 统计显著切换、KV 复用感知淘汰/路由）环环相扣，全部围绕"让基础设施感知智能体行为"这一个中心思想；实验扎实（真实轨迹回放、生产级基线、256 卡规模、3072 卡仿真），代码开源。

**启发**：做 LLM serving 的下一步不在单点 kernel 优化，而在**系统与工作负载的共演化**——上下文工程（harness）的行为会反过来重塑推理基础设施的最优设计，这正是"Evolving Infra"这个名字的含义。对研究者而言，"把应用层语义信号引入系统层决策"是一条清晰且可复制的选题主线：KV 管理之外，token 预算控制、投机解码的草稿策略、缓存定价（比如把 KV 复用折算进计费）都可以用同样的思路重做一遍。
