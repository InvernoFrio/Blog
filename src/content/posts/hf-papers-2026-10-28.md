## 一、研究背景与动机：为什么"格式一致"还远远不够

LLM 的强化学习后训练（RLHF / RLVR）天然是**双引擎结构**：一个自回归 sampler 负责采样生成序列，一个 learner 负责在采样序列上计算重要性比并做策略更新。RLVR 数学推理的爆发让这套流水线的吞吐成为核心成本，于是"原生低比特"（native low-bit）计算被寄予厚望——特别是 NVIDIA 提出的 NVFP4 格式：4-bit E2M1 数值 + 每 16 个数一个 E4M3 block scale + 外层 FP32 scale，理论上能把 GEMM 算力再翻一倍。

问题在于：**RL 比 SFT 对数值不一致敏感得多**。PPO/GRPO 类目标里的 importance ratio

$$\rho_t(\theta)=\frac{\pi^L_\theta(a_t\mid s_t)}{\pi^L_{\bar\theta}(a_t\mid s_t)}$$

直接把 learner 和 sampler 算出的 token 概率送进 clip 决策（式 1）。两个引擎只要在**同一批权重、同一数值格式**下有系统性的执行差异，就会持续污染梯度。已有的"量化采样 / 精度对齐 / 量化感知 RL"工作大多假设：只要权重和格式名对齐了，策略评估就是一致的。

本文的核心发现恰恰相反：**NVFP4 的格式名并不构成一个完整的执行规范**。舍入指令、规约顺序（reduction order）、padding、router 权重与输出 cast 插在计算图的哪个位置——这些都由实现自由决定，而它们全都影响最终 logprob。作者把这类差异命名为**执行鸿沟（execution gap）**，并给出系统性的诊断与弥合方案 miniTE。

## 二、核心方法与创新点

### 2.1 执行鸿沟的定量定义

固定参数版本 $\theta$、token ID 与评分上下文，用 teacher forcing 对同一条序列打分，定义纯执行差异：

$$\delta^{\mathrm{num}}_t = \log\pi^L_\theta(a_t\mid s_t) - \log\pi^R_\theta(a_t\mid s_t),\qquad \rho^{\mathrm{num}}_t = \exp(\delta^{\mathrm{num}}_t)$$

固定住版本滞后和采样随机性后，剩下的就是"执行"本身。作者刻意区分了三类比较：**量化误差**（NVFP4 vs BF16，栈内）、**跨栈执行差异**（learner vs sampler）、**实现差异**（同一算子的优化版 vs 参考版）。

### 2.2 NVFP4 到底"定"了什么、没定什么

NVFP4 的重建公式为（式 3，块 $b$、外层 scale $g$、块内最大幅值 $a_b$）：

$$s_b = \mathrm{E4M3}\!\left(\frac{a_b}{6g}\right),\quad c_i = \mathrm{E2M1}\!\left(\frac{x_i}{g s_b}\right),\quad \hat{x}_i = g s_b c_i$$

其中 6 是 E2M1 的最大幅值。公式看似完整，但外层 scale 是整张量还是逐行、舍入用哪条指令、累加顺序如何、router 和输出 cast 在哪进入——全都不在格式规范里。这正是"执行规范（execution specification）"作为诊断与实现单元的价值所在。

### 2.3 三层诊断协议

miniTE 的诊断不是黑盒跑 benchmark，而是三个递进的控制实验（冻结 Qwen3-30B-A3B-Base 检查点，32 prompts / 69,088 matched tokens 做尾部统计，12 prompts × 11 个深度做定位，2,000 次 prompt-cluster bootstrap 给置信区间；栈内自比对是 bitwise 精确的）：

1. **冻结策略打分**：量化执行差异 $\delta^{\mathrm{num}}_t$ 的分布尾部；
2. **路由条件化**：固定目标层的专家分配（MoE 离散路由），只保留连续计算路径的差异；
3. **缩放对照**：只改 sampler 侧 scale 策略，检验能否单方面消除鸿沟。

### 2.4 miniTE 框架：诊断 + 对齐 + 原生 W4A4 数据流

框架的默认训练路径是**原生 W4A4 专家前向 GEMM + BF16 反向**（注意力、非专家模块、反向、优化器状态保持高精度），不改 RL 目标函数本身。工程上的关键洞察是：FP4 算术吞吐只是一部分成本，MoE 专家负载还需要操作数准备、表示转换与 dispatch。因此 miniTE 把 **per-token 量化与 grouped GEMM 优化成一条连通数据流**，围绕数值核心削减重复的准备开销，让 FP4 的算术收益真正落到账面吞吐上。同时提供严格（strict）执行模式作为跨引擎对齐参考，以及可配置数值 recipe、可替换专家算子与可复用诊断器。

## 三、实验结果与分析

### 3.1 执行鸿沟确实存在，且对齐不掉

| 指标（冻结策略，teacher forcing） | BF16 | NVFP4 |
|---|---|---|
| \|δ_num\| 的 P99（nats） | 0.1271 | **0.2911**（配对增量 0.1641，95% CI [0.1311, 0.2005]） |
| 数值-only 比值超出分析 clip 界的 token 占比 | 0.627% | **1.203%** |

也就是说，即使在**没有任何优化器更新**的冻结权重下，NVFP4 就已把跨引擎 logprob 尾部放大了一倍以上。更关键的两个否定性结果：固定目标层专家分配后 FC1/FC2 输出仍有显著差异（对不上的是算子执行而非路由）；只改 sampler 侧 scaling 并不能建立一致性。"权重对齐 + 格式名对齐"被证伪，差异落在执行规范层。

### 3.2 吞吐与学习质量

| 配置（Qwen3-30B-A3B） | 结果 |
|---|---|
| 专家前向模块（同 recipe 对比） | 比 TE U3045 快 **2.46×** |
| 完整 learner 更新吞吐（固定文本，B300 单节点） | **33,540 tokens/s**，为 BF16 的 **1.39×**、TE NVFP4 的 **1.47×** |
| 重复核心实验的 learner 吞吐 | BF16 的 1.33× |
| 长时程 RL 训练 | 持续稳定学习，四个数学 benchmark 全部**优于 naive TE NVFP4**，整体**接近 BF16** |

注意作者的口径很诚实：模块对比衡量的是原生实现收益，完整 learner 更新衡量的是数值路径与实现的**合**成效果，所以 1.39× 才是"到手"的真实收益。另外在 colocated RL 场景的独立测量中，**权重转换与同步**被识别为集成瓶颈——这提示低比特 RL 的下一个瓶颈不在 GEMM 本身，而在权重格式转换/同步链路。

## 四、与 AI 基础设施的关联

这篇论文对 AI Infra 研究者的启发相当直接：

1. **数值一致性应成为 RL 训练系统的一等公民**。任何"训练引擎 + 服务引擎"分离的 RL 架构（同步或异步 off-policy）都需要一个类似 miniTE 的执行诊断套件：冻结策略打分、路由/分配条件化、逐算子对齐检查。这条对 vLLM/SGLang 与训练框架混搭的组合尤其重要。
2. **低比特的收益要用"完整 learner 更新"来核算**。FP4 GEMM 的 microbenchmark 数字会骗人；操作数准备、dispatch、权重转换/同步这些"数据搬运税"才是落地折扣。对推理侧同理：per-token 量化的 kernel 快不快，要看端到端 step time。
3. **"执行规范"是比"数值格式"更正确的抽象层**。格式名（NVFP4/BF16）无法约束舍入、规约、cast 位置；未来的多引擎训练/推理互操作标准，应该把执行规范纳入一致性契约。
4. **MoE 是低比特化的放大器**：离散路由 + 连续专家计算的混合让"对齐"问题多了一个维度（专家分配 replay、router 精度），grouped GEMM 的数据流设计直接决定低比特收益能否兑现。
5. **对资源调度的启示**：权重转换/同步成为集成瓶颈，意味着 colocated RL（训推同卡）调度策略需要把格式转换成本建模进调度器，而不是默认它免费。

## 五、总结与启发

**亮点**：(1) 问题定义锋利——首次把"执行鸿沟"从工程脏活提升为可量化、可诊断的研究对象；(2) 方法论严谨——冻结策略 + 配对统计 + bootstrap 置信区间 + 路由条件化控制实验，否定性结果（scaling 单边调整无效）尤其有价值；(3) 工程完整——诊断器、kernel、Dockerfile 与一键脚本齐开源，33,540 tokens/s 与 1.39× 是完整更新口径而非 cherry-picked kernel 数字。

**不足**：(1) 实验集中在 Qwen3-30B-A3B 与数学 RLVR 任务，稠密模型与更宽任务分布上的泛化性待验证；(2) 反向仍用 BF16，原生低比特反向的稳定性问题留待后续；(3) 权重转换/同步瓶颈被识别但未给出系统性解法；(4) 论文页未给出可直接访问的仓库 URL（作者称已开源，建议读者从 arXiv/项目页跟进）。

**对后续研究的启发**：把"数值路径一致性"做成训练框架与推理引擎之间的**可执行契约**（类似一致性测试套件），可能是下一代 RL 训练系统的标配；而 colocated 训推一体化里，格式转换/同步的成本建模与调度协同，是一个几乎空白但马上会变得很贵的方向。
