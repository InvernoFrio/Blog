一句话概括：把「给定模型、GPU 配额和真实编码会话负载，设计一套完整的 LLM 服务系统并自己决定服务多少并发会话」变成一道可评分的题，然后看 11 个前沿编码智能体能把它做到多好——以及它们在哪里翻车。

## 二、研究背景与动机

LLM 编码智能体（Claude Code、Codex 等）已经能通过实验迭代开发软件，而它们自身的运行恰恰依赖 LLM 服务系统（vLLM、SGLang 等）来执行模型、处理请求。这就产生了一个很有意思的递归机会：**让编码智能体去设计支撑自己运行的服务系统**。服务提供商的真实需求很朴素——模型执行正确、响应及时、成本可控。

然而现有的智能体系统优化基准存在三个缺口：

1. **负载过度简化**。KernelBench、InferenceBench 等基准发的是独立请求或固定 prefill/decode/吞吐场景。请求长度均匀、批量固定时，一个静态 batch 就几乎能追平生产级引擎，连续批处理、paged attention 这些真实部署依赖的技术毫无用武之地。而真实编码智能体负载是长短请求混合、多轮共享上下文持续增长、并行子智能体扇出——前缀复用、显存管理、prefill–decode 干扰才是性能的主导因素。
2. **只看加速比的目标**。既有基准拿相对基线的 speedup 打分，忽略延迟要求和 GPU 成本，还固定了提供负载。真实服务商必须决定「服务多少负载」，同时把 TTFT（首 token 延迟）和 TPOT（每 token 延迟）压在目标内。
3. **只查正确性的验证**。典型验证只对比参考实现或跑测试集。但服务系统还必须在部署负载上满足尾延迟目标、完整执行全部负载（完整 prompt、规定输出长度、流式一致）。投机解码、状态复用、自定义调度这些优化会引入短测试几乎触不到的执行路径，恰恰是事故高发区。

## 三、核心方法与创新点

### 3.1 任务定义与「dollars per dollar」目标

每个任务固定模型 checkpoint、GPU 分配、编码会话负载和服务要求。智能体从一个最小的 Transformers 服务端 `S0` 出发，在时间预算 `B` 内开发出服务系统 `SB`，并自行选择会话并发数 `cB`。允许重写执行引擎、批处理、显存管理、调度、状态复用，但必须保持规定的 checkpoint、精度和推理语义。

核心目标函数：

```
D(SB, cB) = Σ_{i∈R} q_i · v_i / [ d · r · (W/3600) ]
```

其中 `v_i = (p_in·x_i + p_out·y_i) / 10^6` 是请求 i 按固定 API 价格计价的 token 价值（美元/百万 token）；`q_i = 1` 当且仅当该请求的 TTFT 和 TPOT 都达标；`d` 是 GPU 数、`r` 是每 GPU 小时价格、`W` 是测量窗口秒数。再定义毛价值 `G = Σv_i / [dr(W/3600)]` 和达标价值占比 `f = D/G`，于是 **D = G·f**。例：3.65 美元达标 token 价值除以 0.83 美元 GPU 成本 = 4.40 分。

这个目标的设计非常讲究：它同时奖励**容量提升**和**匹配的负载选择**——多接会话能提高毛价值 G，但只有在请求仍然达标的前提下才转化为 D。把「做快系统」和「运营系统」两件事压进了一个指标。

**延迟标定**：开发前用 SGLang 的模型专属 cookbook 配置作为参考操作点，多次回放取 p90 TTFT 和 TPOT 各种子的最大值作为冻结目标 `τ_first`、`τ_token`，为智能体留出波动余量。

### 3.2 有状态负载与闭环回放

用 SemiAnalysis 的 AgentX harness 回放真实编码智能体会话轨迹（隐私保护重构：替换 prompt 和工具内容，保留请求长度、共享前缀、会话拓扑）。关键在于**闭环**：请求要等它依赖的响应返回才能发出，所以服务延迟直接决定测量窗口内能完成多少会话工作——这把延迟和「产出」连了起来，是 open-loop 压测做不到的。共享上下文鼓励前缀复用，而保留的状态和活跃请求又争夺显存；增长的上下文带来复用机会，新会话又用 prefill 挤占 decode——正是这些张力定义了真实的系统设计空间。

### 3.3 开发环境与验证协议

智能体在断网的 Harbor 沙箱（container/Modal 后端）里工作，拿到最小服务端、只读模型权重、参考配置、测量工具和公开的评分流程，自己决定做什么实验、何时发布版本，超时后最后发布的版本即提交物。

验证远不止正确性：在全新部署中用与开发不相交的种子回放，检查完整 prompt、规定输出长度、流式一致性、自然停止（EOS 探针）、与 checkpoint 的生成一致性（参考评分续写）、留出问题的答案正确性；再由审查智能体 + 人工检查代码和录制动作，排除「绕过模型计算」之类的捷径。**只有通过验证的系统才计分**。

### 3.4 实验设置

11 个编码智能体模型（Claude Opus/Sonnet 5.5、GPT 6 Astra / 6.1 Sol / 6 Sol、Kimi K3、Qwen3.8-Max-0902、MiMo V2.6 Pro、GLM 5.3、DeepSeek V4.1 Flash 等，均开最大推理力度），GPT 系用 Codex harness、其余用 Claude Code harness。三个部署：Gemma-4-E4B-it（1×L40）、Qwen3.5 9B（2×L40）、Qwen3.8 27B INT4（2×L40）。每个智能体-部署对一次 8 小时开发 + 1800 秒最终回放。基线是 SGLang v0.5.19（cookbook 配置）和 vLLM v0.28.0。

## 四、实验结果与分析

### 4.1 端到端结果（dollars per dollar @ 并发 c；TTFT 秒 / TPOT 毫秒为 p90）

关键数字：Claude Sonnet 5.5 在 Gemma E4B 上拿到 **2.97**，是 vLLM 参考的 **4.87 倍**；Opus 5.5 在两个 Qwen 部署上分别是 SGLang 参考的 2.71 倍和 vLLM 参考的 1.80 倍。33 次运行中 **22 次产出可验证系统、13 次超过最强基线**；6 个模型在三个部署上都通过验证，但只有 3 个在三个部署上全面超过基线——可见表现相当不均衡（GPT 6.1 Sol 在 9B 上拿到 2.84，却在 27B INT4 上只有 0.98，还不如基线）。

### 4.2 三条核心发现

**发现一：高价值设计 = 容量提升 × 负载选择协同。** 达到 ≥2 倍基线的运行中，7/17 的负载决策在后续测量中提升了价值，而低于基线的运行只有 2/23。前者的可用回放来得更早（中位 0.90 小时 vs 2.96 小时）——先做快引擎、再放开并发。Sonnet 5.5 在 Gemma 上先把 4 个会话稳住修引擎，再随实现改进把负载提到 32；对照组实验显示同一冻结系统 2 会话只有 1.30、32 会话达 2.97。而 Opus 5.5 在 20 会话回放中毛价值更高但只有 64% 达标，于是明智地退回 16。Kimi 则在识别出长 prefill 干扰 decode 后主动降载。高分系统普遍叠加了更多优化：投机解码、主机内存状态存储、延迟感知调度；跨轮前缀复用则出现在所有被审计的系统中。

**发现二：性能反馈必须放在工作负载语境里解读。** 在 ≥2 倍基线的运行中，49% 的保留决策有「工作负载相关测试」的收益支撑，失败运行只有 25%；未经验证就保留的决策在失败运行中占 40%。最典型的案例是 prompt-lookup 投机解码的取舍：Opus 5 用合成随机文本探针得到零结果，放弃了该优化；Opus 5.5 拿 60 条真实回放响应重测，测到每步 2.09–2.34 个被接受 token，修复模拟器后采纳。对照实验：从同一 checkpoint 分叉两小时，只在获得真实回放反馈的一臂重新采纳投机解码，其服务系统在两个新种子上达标价值高 1.13–1.31 倍。反面案例同样有教育意义：一次 Opus 5.5 运行把并发从 10 提到 16、看到分数从 2.20 涨到 2.99 就保留了配置，最终回放里同一实现的达标占比从 76.0% 崩到 16.8%、分数只剩 0.48——它用了一个异常轻的初始分支条件来验证最终配置，而廉价的 CPU 负载扫描（7.71 秒）本可揭示种子分布差异。

**发现三：验证必须匹配部署负载。** 提交时只有 5/33 个条目对自然停止或长上下文做过记录在案的检查。Qwen3.8-Max-0902 收紧准入保护 TPOT，只用短 prompt 和 11 请求的小回放自测，结果提交策略让一整段允许长度的 prompt 永远进不了执行，最终评估在 315K token 的输入上卡死。Kimi 修完数值错误后隔离测试通过，但同一前缀第二次插入缓存时崩溃，该异常在最终评估中复现。正面例子是 Opus 5.5 在 Gemma 上主动缩小缓存池强制触发抢占和恢复路径，暴露了未初始化缓存存储导致的无效输出（一个先于本次改动就存在的缺陷），修复后 3/3 压力测试通过、回滚修复则 0/3。

### 4.3 测量窗口的消融

固定实现与并发下，300 秒窗口平均给出 1800 秒分数的 1.42–1.70 倍，900 秒窗口则是 1.04–1.21 倍；把窗口从 300 秒延长到 1800 秒可把跨种子变异系数从 0.37 降到 0.19。结论：900 秒级中等回放足以指导开发，但最终评测必须用长窗口压掉方差。

## 五、与 AI 基础设施的关联

这篇论文对 AI Infra 研究者的价值可能比对 Agent 研究者更大：

1. **「AI 设计 AI 系统」从口号变成可度量的赛道**。AlphaEvolve、ADRS、Vortex 证明了智能体能生成 kernel 和算法，但 ServerBench 第一次把「完整的、专用的服务系统」作为设计对象，且带经济目标和独立验证。它给出的三条发现（容量-负载协同、工作负载相关实验、路径覆盖验证）直接可以当作 AI4AIInfra 智能体的行为规范。
2. **指标设计的示范**。dollars per dollar = G·f 的分解让「吞吐」和「SLO 达成率」不再对立，而是乘法关系——这对 LLM 推理服务的容量规划、定价、准入控制研究都是可借鉴的评价框架。把「服务多少负载」交给被测系统自己定，逼出了真正的运营智能。
3. **闭环回放是对 open-loop 压测的降维打击**。请求依赖响应、服务延迟决定完成量——这更接近智能体/RAG 场景的真实流量。做推理调度或 KV cache 研究的同行值得借鉴这种「会话拓扑 + 共享前缀 + 状态竞争」的负载构造方法。
4. **验证工程的启示**。投机解码、状态复用、抢占恢复引入的执行路径需要专门的对抗性测试（边界准入、重复前缀、强制抢占）。这对任何改 vLLM/SGLang 调度内核的系统工作都是直接可复用的测试清单。
5. **智能体能力的分化信号**。33 次运行 22 通过、13 超基线，且失败集中在长上下文准入、跨请求状态这类「全局一致性」问题上——说明当前编码智能体做局部代码优化已足够强，做「系统级不变量维护」仍不可靠。这为推理系统的自动化调优/自演化平台（MLOps 方向）划出了当前的能力边界。

## 六、总结与启发

**亮点**：(1) 任务定义真实——真实会话轨迹、闭环回放、经济目标，三者缺一不可地逼出真问题；(2) 验证协议严谨，独立重建 + 留出种子 + 代码审查，把「刷分捷径」堵得很死；(3) 轨迹分析不是罗列分数，而是给出可执行的设计经验（如：先容量后负载、用工作负载响应而非合成文本校准投机解码、修完 bug 重跑受影响的检查）。

**不足**：只有 3 个模型-硬件部署、一个编码轨迹来源；重构输入保留了负载结构但不复现原始任务；闭环回放与开放到达的生产流量不同；固定价格的 token 价值不含开发成本，测的是部署效率而非真实利润；观察性分析不能建立因果，需要重复运行分离智能体方差与负载方差。

**对后续研究的启发**：这套框架可以向训练系统设计（给定集群和作业负载，智能体设计并行策略与调度）、编译器/算子优化的端到端集成、以及多智能体协同设计系统扩展。对于做 LLM 推理服务的团队，最实用的三条是：用 dollars per dollar 类的复合指标替代裸加速比；为每个优化显式构造能触发其执行路径的压力测试；在工作负载真实分布上（而非合成探针上）做实验决策。
