## 二、研究背景与动机

LLM Agent 的长任务已经能跑几百轮：反复推理、调用工具、读取环境反馈。轨迹越长，**KV cache 的 I/O 与存储就成为主导成本**——论文统计显示，在 Agent 的 API 成本里 KV cache 读取占到 **82.4%**。同时轨迹可能超出模型最大上下文长度，导致关注的 KV 数量或位置范围越界，任务准确率严重下降（长上下文失效问题）。因此，如何控制「活跃 KV cache」成为 Agent 高效可靠运行的关键。

现有主流做法是 **context engineering（上下文工程）**：删减（trim）或摘要（summarize）历史消息来压缩 cache。但它有一个结构性矛盾：

- **改历史 = 作废前缀**。编辑早期消息会改变轨迹前缀，其后所有 KV 状态全部失效，必须 re-prefill 保留下来的后缀。改得越早，要重算的后缀越长，成本越贵。
- **于是 harness 都在拖**。Claude Code、Codex 等常见 harness 只能推迟到上下文长度触达阈值才一次性摘要/删减，只保留最近几轮以控制 re-prefill 长度。
- **激进压缩必然丢信息**。摘要阈值卡掉中间轮次的关键信息，形成「**re-prefill 成本 vs 任务准确率**」两难。

论文给出了一组很直观的实证（GPT-OSS-120B，BCP 前 100 题）：

| Context engineering 策略 | 相对全上下文的成本 | 准确率 |
|------|------|------|
| Trim（只留最近 12 轮工具响应） | **1.85x**（反而更贵！） | — |
| Summary（48K 阈值） | 约省 7% | **-5 个百分点** |
| Cache engineering（drop 旧工具响应 cache） | 同时更便宜 | 同时更高 |

Trim 之所以更贵，就是 re-prefill 反复重算后缀造成的。这组数据直接说明：**问题不在「历史没用」，而在「修改文本」这个动作本身**。

## 三、核心方法与创新点

### 3.1 Cache engineering：不动文本，只动 cache

本文提出 **cache engineering**：Agent 直接控制活跃 KV cache（进入后续注意力计算的 KV 状态），**完全不修改文本轨迹、不触发 re-prefill**，所有保留的 KV 状态原样复用。这使 Agent 能在给定成本预算内增量丢弃旧 KV、保留更多后缀信息。形式化上，在标准的 append 之外新增两个 cache 操作：

**append（追加）**——标准推理更新：

```text
append(x_{t+1}): C ← [C; C_{t+1}]
```

**drop（丢弃）**——从后续注意力中移除选中的 KV 条目，保留状态、位置编码、文本轨迹一律不变：

```text
drop(P): C ← C \ {C_i : i ∈ P}
```

**repos（重定位）**——重新排布保留 key 的位置编码并重置下一个 append 的位置索引。对 RoPE 而言，把 key K 从位置 p 移到 q 只需一次矩阵旋转：

```text
K ← R(q) R(p)^{-1} K
```

价值 V 不变。这一步的意义在于**把位置编码索引与逻辑 token 长度解耦**：默认位置索引随轨迹增长，cache 再小也可能撑爆模型的位置上限；repos 之后，r 个保留条目占据位置 0..r-1，探索空间不再被位置墙卡死。

再用**缓存操作序列** o_{1:m} 对整个过程做确定性描述：固定模型下，从空 cache 出发，操作序列唯一决定当前 cache 状态。

### 3.2 关键发现：cache 状态是「历史依赖」的

这是全文最重要的系统层洞察。标准 KV cache 里，token 前缀**完全决定**缓存状态，所以 prefix matching 就能安全复用。而 cache engineering 里**同样的 token、同样的保留位置，不同操作历史会产生不同 cache**：

- 轨迹①：append A、B、C 后再 drop A → C 是在看过 A、B 的条件下算的；
- 轨迹②：先 drop A 再 append C → C 看不到 A；
- 轨迹③：从 B 起步 append C → B 的 KV 也不再以 A 为条件。

三条轨迹都保留 B 和 C，但 C 的 KV 三条全不一样。**只按 token 前缀匹配去复用 cache，会拿到语义错误的状态**。因此正确复用必须同时追踪 token 历史和 cache 操作历史。

### 3.3 AKV 服务引擎：无状态接口，有状态服务

为此作者协同设计了 **AKV** 服务引擎，原则是 *stateless interface, stateful serving*：

- **接口层**：兼容现有 OpenAI 风格 API，Agent 照常提交 messages，外加一段 `cache` 字段声明 drop/reposition 指令即可，不需要知道哪些 KV 还驻留在服务端。
- **扩展 radix tree**：把 cache 操作历史编码进 radix tree 的分支，区分「token 相同但操作历史不同」的状态，实现正确复用与及时淘汰——上文三条轨迹在树上自然分叉。
- **segment-batch attention**：当所需状态被逐出后需要恢复时，在单次 prefill 中分段批量重建缺失状态，把「restore」开销压到一次 prefill。

### 3.4 策略：tool-response rolling drop + RSI 进化

设计动机来自注意力统计：**旧 token 注意力低、工具响应注意力低于同等位置的助手消息**。于是主策略很朴素——保留全部推理与近期工具响应的 KV，滚动丢弃旧工具响应 cache（保留最近 K=12 轮）。此外还有两种进阶玩法：

- **递归自我改进（RSI）**：把缓存策略的搜索-评估-改进交给 LLM 自己做（用 MiniMax-M2.7 在 20 个 BCP 任务上迭代）；
- **Cache-as-Tool**：把缓存管理暴露成工具，Agent 自己决定何时降缓存、保留什么。

## 四、实验结果与分析

**设置**：3 个模型（MiniMax-M2.7、GPT-OSS-120B、MiroThinker-1.7-Mini）× 4 个长程基准（BrowseComp-Plus、GAIA-Text、SWE-Verified、xbench-DS）；基线为 Standard（阈值 96K/192K 摘要）与 Text Engineering（48K 摘要）；服务端 8×A800-80GB（4 prefill + 4 decode，TP=4），基于 SGLang。

### 4.3 消融与策略对比（GPT-OSS-120B，各基准前 100 题）

| 策略 | repos | BCP 分数/成本 | SWE 分数/成本 |
|------|------|------|------|
| Standard | ✗ | 56.0 / 13.5 | 41.0 / 19.1 |
| Tool drop | ✗ | 55.0 / 7.1 | 41.0 / 9.4 |
| Reasoning drop | ✓ | 56.5 / 8.2 | 36.5 / 14.2 |

三个结论：**① repos 是点睛之笔**——BCP 通过率从 55% 升到 62%，因为它允许探索突破位置上限；**② 只丢工具响应**，丢推理 cache 反而伤任务；**③ RSI 迭代出的策略**（第 3/6 轮）比手工设计再省 15.6%/17.8% 成本，其中最优策略相对 Standard 共省约 17.8%。Cache-as-Tool 让 Agent 自主管理时，两个模型上都拿到最高分（GPT-OSS 61.0%、MiniMax 64.0%）。

## 五、与 AI 基础设施的关联

这篇论文对 AI Infra 各个方向都有实打实的启发：

1. **LLM 推理服务**：前缀缓存（prefix caching）是 vLLM/SGLang 的标配，但其正确性前提是「token 前缀决定 cache 状态」。cache engineering 把这个前提打破了——**缓存键必须从 token 前缀扩展到 token + 操作历史**。扩展 radix tree 给了一个可落地的实现范式，任何要做「可编程 cache」的推理引擎都要面对这个问题。
2. **Agent 服务成本优化**：KV 读取占 API 成本 82.4%，而 Agent 负载天然多轮、工具响应冗长且低注意力。按消息角色做差异化 KV 淘汰（工具响应先丢、推理保留）比 token 级重要性启发式更符合负载特征，直接指导推理系统的 cache 淘汰策略设计。
3. **KV cache 分层与换入换出**：drop 保留「文本在、KV 不在」的状态，segment-batch attention 的按需重建近似于 cache 的「换入」路径。与 GPU-CPU-SSD 分层存储结合，可以把「活跃注意力 cache」和「物理驻留 cache」彻底解耦——前者由 Agent 编程控制，后者由系统调度。
4. **位置编码与位置无关缓存**：repos 用 RoPE 旋转矩阵做零重算重定位（K ← R(q)R(p)⁻¹K），与 MLA 位置无关缓存等技术同源，为长程 Agent 的「位置墙」提供了绕行通道。
5. **AI4AIInfra / 自优化系统**：RSI 让 LLM 自己搜索缓存策略并再降 17.8% 成本，是「用 AI 优化 AI 系统」的又一实例；把系统旋钮（缓存操作）形式化成可编程接口，正是让 LLM 能够调优系统的前提。
6. **训练系统与调度**：思路可迁移到训练侧的激活/梯度缓存管理与检查点策略；对调度器而言，「避免 re-prefill」意味着把重算开销从调度路径上拿掉，批准入和抢占策略都可以围绕「保留 cache 命中」重新设计。

## 六、总结与启发

**亮点**：① 把「改文本」换成「改 cache」，干净地解开了 re-prefill 成本与信息保留的两难，方法论层面很优雅；② 「cache 状态历史依赖」的发现具有普适价值，重新定义了推理系统缓存复用的正确性条件；③ 算法-系统协同（操作原语 + AKV 引擎 + RSI 策略）完整闭环，三模型四基准的数字也扎实。

**不足**：策略空间探索仍浅（主策略是手工启发式 + 小规模 RSI）；未涉及用训练让模型适配 cache engineering；暂不支持线性注意力模型；结论主要在 A800 + BF16 上验证，对其他硬件/量化配置的泛化性待考。

**启发**：KV cache 的控制权正在从「推理引擎内部」上移到「Agent/应用层」，这是系统接口演化的重要信号——未来推理服务可能要像暴露 file descriptor 一样暴露 cache 操作接口。对研究者而言，「缓存操作序列」是一个新的可编程维度：策略学习、RL 训练、多 Agent 共享缓存都可以在它上面展开。对工程实践者而言，即使不上 AKV，「工具响应先丢、推理保留、适时重定位」这条纪律已经可以直接用于降低 Agent 的账单与长任务失效。
