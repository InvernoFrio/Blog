## 先用一句话回答

**AI Infra，也就是 AI 基础设施，研究怎样组织计算、内存、数据和机器，让模型能够被高效地训练、部署和使用，并满足质量、成本与可靠性的要求。**

这里的“基础设施”包括硬件，也包括运行在硬件上的软件系统。一个张量怎样存放、一次矩阵乘法怎样执行、八张 GPU 怎样协作、上千个请求怎样排队，以及训练中途机器出故障怎样恢复，都可以是 AI Infra 问题。

它同时是一类工程工作和一类研究方向。工程上，要搭建并维护可以使用的系统；研究上，要提出新的执行、存储或调度方法，用实验解释方法在什么条件下有收益。研究对象可以小到一个 GPU kernel，也可以大到一整个训练或服务集群。

## 从一个具体任务理解它

假设我们要训练一个语言模型，再把它做成聊天服务。

起初，一台机器就能跑通训练。随着任务变大，新的问题逐渐出现：数据读取跟不上计算，模型和训练状态放不进显存，增加 GPU 后通信占掉大量时间。训练结束后，虽然权重可以加载，长对话的缓存仍可能耗尽显存；并发请求又会排队，用户等很久才看到第一个字。

“模型会不会回答”与“模型怎样在这些条件下持续运行”需要一起解决。AI Infra 关注后面这组系统问题，并把模型行为和数值要求当成设计约束。例如，改变浮点精度或缓存格式时，除了测速度，还要检查误差与任务质量。

下面这张图按一次项目的生命周期展开。实际系统中，这些环节会反复交互。

```text
原始数据 → 清洗、分词、读取 → 训练循环 → 保存模型 → 推理服务 → 用户
                │               │                      │
                │        前向、反向、更新参数      请求排队、批处理、缓存
                │               │                      │
                └──────── 框架、编译器与运行时 ─────────┘
                                │
                        算子 / GPU kernel
                                │
                    GPU、显存、CPU、存储与网络

资源调度、监控、故障恢复与版本管理贯穿以上环节。
```

## 一张全景地图：六组相互联系的问题

下面按常见问题分成六组，方便定位学习内容。不同团队的职责划分会有重叠，这不是统一的行业分类标准。

| 层面 | 研究什么 | 一个具体问题 | 常用观察量 |
| --- | --- | --- | --- |
| 算子与设备执行 | 把数学计算映射到硬件，安排线程、分块和数据复用 | 为什么同一个矩阵乘法，换了尺寸就变慢？ | kernel 时间、数据流量、数值误差 |
| 编译与运行时 | 将模型图转换为可执行程序，选择与融合算子，管理执行依赖 | 为什么首次运行很慢，换输入形状又重新编译？ | 编译时间、稳态延迟、重新编译次数 |
| 内存与状态管理 | 安排权重、激活、梯度、优化器状态和推理缓存 | 权重放得下，为什么训练或长对话仍然显存不足？ | 峰值显存、缓存容量、拷贝与重算成本 |
| 分布式训练与通信 | 在多张卡、多台机器上拆分工作，交换数据并保持训练语义 | 从 1 张卡扩到 8 张卡，为什么没有快 8 倍？ | step 时间、通信时间、扩展效率 |
| 推理与服务 | 处理请求、组织批次、复用缓存、路由并扩缩容 | 总吞吐提高了，为什么用户等待却更久？ | 首 token 延迟、生成间隔、尾延迟、有效吞吐 |
| 数据、存储与平台 | 提供训练数据和模型文件，分配资源，记录实验与恢复故障 | GPU 为什么在等数据？训练中断后能否接着跑？ | 读取吞吐、空闲时间、恢复时间、失败率 |

硬件是这些工作的共同基础：GPU 提供计算与片上存储，显存保存大量模型数据，网络连接机器，持久化存储保存数据集与检查点。软件要针对它们的容量、带宽和延迟组织工作。硬件型号或 GPU 数量相同，系统表现也可能因工作负载与软件设计而不同。

### 算子为什么是一个好的入口

考虑 `y = relu(x + bias)`。分开执行时，加法的结果可能先写入显存，随后被 ReLU 读回；融合执行可以直接使用刚算出的值。数学关系很简单，但数据移动与启动次数会影响时间。

这就是现有[算子专题](../../operators/overview/)的位置：从一个小计算出发，学习布局、执行、归约、分块与测量。它提供分析工具，后面可以用这些工具解释整个训练或推理过程。

### 编译器怎样把模型交给设备

框架表达“要算什么”，编译器尝试改写计算图、生成或选择 kernel，运行时负责把工作提交到设备并处理依赖。一个表达式不一定对应一个 kernel，几个表达式也可能被融合。

例如 `torch.compile` 涉及图捕获、图优化与后端生成代码。阅读它时，可以带着“哪些部分能编译、为什么重新编译、融合能省掉什么成本”这些问题进入，而不是先记一串组件名字。具体机制见 [PyTorch 编译器文档](https://docs.pytorch.org/docs/stable/torch.compiler.html)。

### 显存里不只有模型权重

训练需要前向激活、梯度和优化器状态；推理通常需要保存历史 token 的 KV Cache。它们的规模受到 batch、序列长度、模型结构和数值表示的共同影响。

容量不足时，可以拆分状态、重算中间结果，或把部分数据移到其他存储层。每种方法又会引入计算或传输成本，所以“少占显存”必须和“需要多少时间”放在一起判断。

### 多张卡需要交换什么

数据并行让不同设备处理不同样本，并交换梯度；张量并行把某些层的计算拆到不同设备；流水线并行把不同层分给不同设备。这些方式交换的数据、发生通信的时机和负载均衡要求都不同。

多卡扩展要分析计算与通信的比例、它们能否重叠，以及是否有设备在等待其他设备。现有 LLM 专题的[分布式训练](../../../llm/from-scratch/distributed/)可以作为入口；通信操作的具体语义可对照 [PyTorch Distributed](https://docs.pytorch.org/docs/stable/distributed.html)。

### 服务要处理许多不同的请求

一个用户输入很长，另一个用户正在逐字接收回答。把谁放进下一批、给谁分配缓存、一个请求结束后怎样补进新的请求，会影响双方的响应体验。

因此，推理系统同时要考虑吞吐和延迟。接下来先读[Prefill、Decode 与 KV Cache](../../inference/prefill-decode/)，建立“一次请求到底做了哪些计算”的基础，再理解批处理与调度。

### 数据与可靠性也会限制计算

GPU 需要持续收到数据。如果数据读取、解压或分词跟不上，GPU 即使很强也会等待。一个训练检查点则需要保存足够的状态，才能在故障后正确续训；保存太频繁会占用时间，保存太少又可能损失较多已完成工作。

平台层还要决定任务使用哪些资源、怎样观测异常、怎样管理模型与实验版本。这里会用到容器和集群调度等通用系统知识，但学习时应从实际的资源与故障问题进入。

## 它和模型研究、应用开发怎样连接

三者可以在同一个项目中协作，也可能由同一个人完成。下面比较的是关注的问题，而不是给岗位划边界。

| 关注方向 | 针对聊天模型提出的问题 | 怎样判断进步 |
| --- | --- | --- |
| 模型与学习算法 | 换结构、数据或训练目标，能否提高回答能力？ | 损失、任务评估与行为表现 |
| AI Infra | 在指定质量与负载下，怎样训练得更快、服务得更稳、成本更低？ | 性能、资源成本、可靠性与质量检查 |
| 应用开发 | 怎样把模型接入检索、工具与界面，完成用户任务？ | 任务完成率与实际使用体验 |

这些方向也会互相改变条件。例如 GQA 通过让多组 query 共享较少的 key/value heads，改变了模型结构，也减少了常规 KV Cache 的数据量。阅读这样的工作时，既要理解模型质量，也要分析系统收益。见 [GQA 原论文](https://arxiv.org/abs/2305.13245)。

AI Infra 的范围也不限于 LLM。视觉、多模态与推荐模型同样需要计算、通信和存储系统。本栏目从语言模型开始，是为了用一套熟悉的任务贯穿这些问题。

## “更快”到底指什么

一次优化必须明确工作负载、计时范围和约束。单个 kernel 更快，整个任务未必同比例变快，因为数据准备、通信或排队可能占主要时间。

假设原任务用 100 毫秒，其中目标 kernel 用 20 毫秒。把它加速两倍，其他部分保持不变，总时间变为 90 毫秒，整体加速约为 1.11 倍。这是一个教学算例，说明为什么必须先看时间花在哪里。

训练常看完成一个 step 或处理有效 token 的时间，同时保持训练语义与质量目标。服务则需要固定 prompt 长度、输出长度和请求到达方式，观察延迟分布。平均值相同，也可能有一组请求等得特别久；p99 表示约 99% 的观测值不超过这一延迟。尾延迟为何影响大规模服务，可延伸阅读 [The Tail at Scale](https://research.google/pubs/the-tail-at-scale/)。

**GPU 利用率、吞吐、成本与用户体验要结合着看。** 有更多工作在设备上运行，不自动表示用户等待更短。显存长期被占用，也不直接说明这些内存提高了有效产出。

一次可复查的性能判断至少应该说明：运行的任务是什么，设备与软件环境是什么，测量哪段时间，数值与质量有没有变化，以及收益出现在哪些负载条件下。

## 本栏目怎样学

不必等学完所有分支才动手。先读总体概览，把问题放到地图上，再按手头目标选择路径。

| 学习阶段 | 从哪里进入 | 完成后应该能解释什么 |
| --- | --- | --- |
| 认识全貌 | 当前这篇概览 | 一个问题属于计算、内存、通信、服务还是平台，为什么会互相影响 |
| 理解一次计算 | [算子导览](../../operators/overview/) → 布局 → 性能 → Triton → Softmax → GEMM → 在线 Attention | 数据在哪里、谁来计算、结果是否正确、时间花在哪里 |
| 理解一次请求 | [推理入门](../../inference/prefill-decode/)与 CPU 缓存实验 | Prefill 与 Decode 的工作有什么不同，缓存为何随上下文增长 |
| 理解训练扩展 | [从零训练 LLM](../../../llm/from-scratch/overview/)中的训练、缩放与分布式章节 | 训练有哪些状态，多卡需要交换什么，怎样检查训练过程 |
| 继续深入 | 后续补充分页缓存与服务调度、编译、多卡系统和平台专题 | 根据瓶颈选择优化，并报告适用条件和代价 |

目前 AI Infra 已上线总体概览、算子专题和推理入门；最后一行是继续扩展的方向。理论与 CPU 实验可以先在普通电脑上完成，GPU 性能结论需要在相应设备上实测。

## 用五个问题检查理解

1. 模型权重可以放进显存，为什么还可能无法训练，或无法服务长对话？
2. 把一个 kernel 加速两倍，为什么应用响应可能只快一点？
3. 增加 GPU 后，新增的通信与同步成本来自哪里？
4. 每秒生成的总 token 变多了，为什么单个用户可能等得更久？
5. GPU 在等数据时，应该先检查哪段数据路径？

现在不需要掌握每种实现。能把这些现象和状态容量、时间占比、设备协作、服务调度、数据供给联系起来，就已经有了继续学习的方向。
