## 文本到 token 是一个建模决定

本实验把 UTF-8 编码的每个字节作为 token，ID 为 0–255；BOS、EOS、PAD 分别为 256、257、258。无需训练分词器，无未知字符，编码完全可逆。代价是序列较长：多数常用汉字有三个字节，一个 token 可能只是字符的一部分。

现代子词分词器用更大的词表换更短的序列。BPE 可以从字节开始，反复统计相邻对，合并最常见的一对，并保存合并规则。例如训练串 `a b a b a` 中 `a b` 出现两次，先合并为 `ab ab a`。应用到新文本时使用已学规则；不能临时重新统计测试文本来改变词表。

这个小模型先用字节词表，是为了把训练过程做完整。升级时应在训练语料上学习分词器，固定版本与特殊 token，并重新计算 embedding、输出头、上下文长度和吞吐。替换词表后，原有检查点通常不能直接加载。

## 字符、字节、token ID 是三个层次

Python 字符串中的 `中` 是一个 Unicode 字符，UTF-8 将它编码为三个字节：`[228,184,173]`。本实验直接把这三个数作为三个 token ID。因此“上下文 64”指最多 64 个字节 token，而不是 64 个汉字，也不是 64 个词。

```python
text = "中"
raw = text.encode("utf-8")
print(list(raw))
print(raw.decode("utf-8"))
```

预期打印 `[228, 184, 173]` 和 `中`。如果只解码前两个字节，字符还不完整；严格解码会报错。这解释了生成时为何可能出现乱码：模型一次选择一个字节，它并没有通过词表自动保证整个字符的编码合法。

ID 的大小只是查表地址。228 与 184 的数值差，没有被当作语义距离送入网络；输入直接选择 embedding 表第 228、184 行。训练会调整这些行向量，ID 本身保持不变。

子词分词器是另一种压缩折中。更长的常见片段可以占一个 ID，减少序列长度，但需要更大的 embedding 和输出表。长序列增加 Attention 成本，大词表增加分类与参数成本，因此词表大小并不是越大越好。

## BPE 的训练规则与使用规则怎样分开

用一个不跨文档统计的玩具语料 `abab`、`abac`。初始单位是字符，相邻对 `ab` 出现 3 次，`ba` 出现 2 次，`ac` 出现 1 次。先学习合并 `a + b → ab`，两篇文档变为 `[ab,ab]` 和 `[ab,a,c]`。

重新统计当前符号的相邻对，`(ab,ab)`、`(ab,a)`、`(a,c)` 都出现一次。这时算法必须有固定的平局规则；没有唯一的下一步，不能只凭原始字符对频率继续合并。每一次合并都会改变后续统计对象。

训练结束后，分词器保留词表和有顺序的合并规则。对新文本 `abac`，应用已学规则得到 `[ab,a,c]`；不是针对这篇新文本重新学习一套分词器。把验证文本用于重新拟合规则会改变实验条件，也可能泄漏验证分布。

真实 byte-level BPE 还有字节起点、预切分、特殊 token 与边界处理等细节。这个例子只解释合并机制，不把一个几行玩具实现当成生产 tokenizer。即使显示出来的 token 字符串一样，版本不同的词表 ID 和合并顺序也可能不同，检查点必须绑定 tokenizer 版本。

## 先分文档，再制作窗口

随附 `demo.jsonl` 每行是 `{"text":"..."}`。`load_documents` 做 NFC 归一化、去首尾空白和精确去重；`split_documents` 使用固定种子，将约 20% 的独立文档作为验证集。

如果先把一篇长文章切为窗口，再随机把窗口分到训练和验证，它们可能共享大量原文。验证 loss 会因此过于乐观。生产语料还需要近似去重、来源分组或时间切分，以及评测题污染检查；本实验的精确去重没有完成这些工作。

原文件 SHA-256 被保存在检查点里。即使只修改空白，哈希也会变；续训会拒绝不同文件，防止无意改变实验条件。归一化后的内容相同与原始文件相同是两种不同的判断。

## 标签移动一位到底是什么

对于序列 `[BOS, A, B, EOS]`：

```text
输入 x:  BOS    A      B
标签 y:  A      B      EOS
```

位置 $t$ 的隐状态只能读取 $x_{\le t}$，监督它预测下一项 $x_{t+1}$。如果输入和标签完全相同，模型会学习复制当前位置，损失可能很漂亮，却无法证明 next-token 预测成立。

窗口长度为 $T$ 时，读取 $T+1$ 个 token，前 $T$ 个作输入，后 $T$ 个作标签。实验以步幅 $T$ 切窗，边界有一个 token 作为下一窗口的输入，因此每个目标恰监督一次。下一窗口没有更早的历史；这是一种明确的短上下文近似。

## 窗口边界为什么重复输入，却不重复目标

假设完整序列为 `[BOS,A,B,C,D,EOS]`，窗口长度为 3。第一个窗口读取前 4 项，输入 `[BOS,A,B]`，目标 `[A,B,C]`；第二个窗口从原索引 3 开始，输入 `[C,D]`，目标 `[D,EOS]`，再补齐。

这里 C 先作为第一窗的目标，又作为第二窗的输入。这并没有重复监督 C：目标列表拼起来正好是 `[A,B,C,D,EOS]`，每一项只出现一次。共享边界 token 是为了让第二窗还能根据 C 预测 D。

但第二窗的 D 预测只看到 C，不能看到更早的 A、B。切窗确实改变了可用上下文。这是基线为了简单而作出的取舍，不要把“每个目标都监督一次”误认为“每个目标都能读取整篇文档”。扩大窗口、重叠窗口或连续状态都可能改变这个取舍，同时也要重新计算目标是否重复计权。

## PAD 与 EOS 为什么不同

EOS 是需要学习的目标，告诉模型一篇文档或一段回答可以结束。PAD 只是补齐批次，输入用 PAD ID，标签用 `-100`，被 `ignore_index=-100` 排除。

```python
loss_sum = F.cross_entropy(
    logits.flatten(0, 1), labels.flatten(),
    ignore_index=-100, reduction="sum",
)
count = (labels != -100).sum()
loss = loss_sum / count
```

本实验只有右侧 padding，加上因果遮罩，真实 token 不能看到尾部 PAD，因此不必再为这些有效位置遮住 PAD。改成左侧 padding、双向注意力或多文档 packing 后，这个推理不再适用。

本实验一条窗口只属于一篇文档。生产环境为了减少 padding 会 packing 多篇文档，需要同时确定文档间是否允许注意力，以及 position ID 是否重置；加入 EOS 并不自动阻断注意力。

## 多文档 packing：结束标记不会自动隔离内容

若把两个样本 `[BOS,A,EOS]` 与 `[BOS,B,EOS]` 拼成一行，普通下三角遮罩会允许后面的 B 读取前一篇的 A。EOS 只是一个可学习 token；它不是强制切断计算图的墙。

如果目标是独立文档训练，可给每个位置记录文档 ID，再设允许条件为“key 不在未来，且 query 与 key 属于同一文档”。得到块状下三角遮罩。位置编号是否在每篇文档重置，也要与位置机制一起定义。

如果目标是让多篇文档构成连续上下文，允许跨文档读取可以是有意的设计。两种方案都能运行，关键是训练目标与实现一致。只把标签设为 `-100` 控制的是是否直接计入 loss，不能控制其他位置是否读取它。

**练习。** 一条输入有 2 个真实目标和 3 个 PAD，真实目标损失为 1、3。正确均值是 2；若除以总长度 5，得到 0.8。补更多 PAD 会进一步让这个错误 loss 下降，即使真实预测没有改善。这是一个很直接的诊断信号。

## 可检查的实践

用 `make_windows([{"text":"AB"}], 5)` 查看结果。输入应是 `[256,65,66,258,258]`，标签为 `[65,66,257,-100,-100]`，有效目标数为 3。

把相同文档添加两次，独立文档数应不增加。再用两个相似但不相同的句子测试：当前精确去重会保留两者。由此提出升级方案：使用相似度或 MinHash 做近似去重，再检查训练与验证是否共享近重复。
